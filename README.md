# STM32F407 CAN 网关与车载诊断栈

基于 **STM32F407ZGT6** 的 CAN 网关：接收 F103 记录仪节点的现场数据，在本机屏上显示，同时通过 CAN、UDS 诊断和以太网三种出口对外提供。

> 配套节点工程（F103 工业记录仪）为独立仓库，不在本仓库内。

---

## 1. 硬件与角色

| 项 | 内容 |
|---|---|
| 主控 | STM32F407ZGT6，168 MHz，1 MB Flash / 128 KB RAM |
| 以太网 | W5500（SPI），三个服务端口并发 |
| 显示 | ST7789 1.54" 240×240，SPI3 |
| 输入 | EC11 旋转编码器（TIM4 编码器模式） |
| 总线 | CAN1 + CAN2 双通道，均 500 kbps，11 位标准帧 |
| 角色 | 双板系统中的**网关**：F103 采集 → CAN → 本机显示 / 诊断 / 网络 |

```
F103 记录仪 ──CAN 500k──> F407 网关 ──SPI──> W5500 ──Ethernet──> PC
  (采集节点)                │                                   ├ 5000 文本命令
                            └──SPI──> ST7789 (LVGL 界面)         ├ 502 Modbus TCP
                                                                 └ 80  HTTP
```

## 2. CAN 报文分配

| ID | 方向 | 内容 |
|---|---|---|
| `0x080` | 记录仪 → 网关 | 故障告警（通道 / 原因 / 计数） |
| `0x101` | 记录仪 → 网关 | 温度 ×2、湿度 ×2、气压 ×4 |
| `0x102` | 记录仪 → 网关 | 序号 ×2、状态位、**帧布局版本**、RTC ×4 |
| `0x103` | 记录仪 → 网关 | ax / ay / az / vbat |
| `0x104` | 记录仪 → 网关 | gx / gy / gz / light |
| `0x201` | 网关 → 记录仪 | 命令码 |
| `0x301` | 记录仪 → 网关 | 命令应答 |
| `0x2E0` | 网关 → 记录仪 | ISO-TP 请求（诊断 / OTA） |
| `0x3E0` | 记录仪 → 网关 | ISO-TP 响应 |

`0x102` 的**帧布局版本**是两端的一致性闸门：版本不匹配时网关拒绝解析 `0x103`/`0x104`，避免字节按错误布局解出「合理但错误」的数值。

### 总线调度上的两个坑

- **F103 只有 3 个发送邮箱**，一拍发 4 帧时第 4 帧必然撞满。若直接放弃，`0x104` 一帧都发不出去；姿态解算需要加速度与角速度同拍，交替发送会让两者永远差 100 ms。
  解决：撞满时退让 1 ms 重试（`CAN_TX_SendStdWait`）。
- 退让带来的副作用是**邮箱长期占满，诊断应答帧被饿死** —— 现象是 315 块 OTA 在第 8、20 块随机失败并报 `NRC 0x73`（块序号错），实际原因是应答帧丢失导致整块重传。
  解决：关键帧撞满时撤销最近一帧遥测再抢占（`CAN_CancelTransmit`），遥测丢一帧只是曲线少一个点。

### 双通道（CAN2）与跨通道路由

CAN2 挂在 **PB12 / PB13（AF9）**，与 CAN1 同样配置成 500 kbps
（APB1 42 MHz ÷ 预分频 4 = 21 个时间量子：同步段 1 + 段一 16 + 段二 4）。
两个通道**共用 28 个滤波器组**：CAN1 用 14~27，CAN2 从 14 起（`SlaveStartFilterBank = 14`）。

加第二个通道是为了把「现场总线」和「诊断/标定总线」在物理上分开。
代价是 PB12/PB13 与未来的 RMII（`ETH_RMII_TXD0/TXD1`）冲突——真要上 RMII，
得先把 W5500 从 SPI2 挪到 SPI1 腾出这两根脚。这一步 2026-11-22 已经做了（见第 1 节引脚说明）。

#### 路由

四条路由，把 CAN1 收到的四类遥测原样转到 CAN2：

```c
typedef struct {
    uint8_t  src_ch;
    uint16_t src_id;
    uint8_t  dst_ch;
    uint16_t dst_id;
} GwRoute_t;

/* 四条路由：F103 的四类遥测帧从 CAN1 转到 CAN2 */
static const GwRoute_t s_routes[] = {
    { 0u, 0x101u, 1u, 0x101u },
    { 0u, 0x102u, 1u, 0x102u },
    { 0u, 0x103u, 1u, 0x103u },
    { 0u, 0x104u, 1u, 0x104u }
};
```

**中断里只做一件事**：把帧塞进 16 深的单生产者单消费者队列，立刻返回。
查路由表、转发、写邮箱全部在主循环里做。这样中断的关中断时间最短，
也不会和 F103 那边 4 帧 / 100 ms 的节奏打架。

推不进去不丢帧：进 8 深的发送后备队列，下一轮再发。

#### 计数与实测

串口 `Q` 命令新增 4 个计数，它们之间的关系本身就是一条守恒式：

| 字段 | 含义 |
|---|---|
| `rf` | CAN1 收到的帧数 |
| `c2rt` | 路由命中的帧数 |
| `c2tx` | CAN2 实际发出去的帧数 |
| `txd` | 后备队列也满、真丢掉的帧数（应恒为 0） |

实测（2026-11-24，F103 每 100 ms 发 4 帧遥测，连续 10 秒）：

```
rf +400    c2rt +400    c2tx +400    txd +0
```

400 帧 / 10 秒 = 40 帧/秒，**转发率 100%，零丢弃**。三个增量相等这一点比总数更有意义——
它证明"收到的每帧都查到了路由，并且都真的发出去了"，不是"收到很多、发出一部分"。

#### 验证状态（如实）

| 项 | 状态 |
|---|---|
| CAN2 外设 / 引脚 / 滤波器 / 中断 | ✅ 已验证 |
| 内部回环自检 `CanGw_SelfTest2()` | ✅ 通过 |
| 真实收发 | ❌ **未验证**，等 SN65HVD230 收发器 |
| 双通道隔离（一路短路，另一路不受影响） | ❌ 未测 |

CAN2 目前停在内部回环模式（`CanGw_Init2(1u)`）。收发器到货后改成 `CanGw_Init2(0u)`，
把总线 B 接到备用节点上，才能做真实收发与隔离测试。

## 3. ISO-TP / UDS 诊断栈

### ISO-TP（ISO 15765-2）

| 参数 | 值 |
|---|---|
| 接收缓冲 | 288 B / 报文（单帧、首帧+连续帧、流控帧） |
| 双缓冲 | 2 × 288 B，按到达序号 FIFO 取包（不按槽号，避免 OTA 块序错乱） |
| BS / STmin | 8 块 / 0 ms（转发侧 STmin 钳到 ≤ 5 ms） |
| N_Cr | 3000 ms |
| 转发流控超时 | 20 ms |

### UDS 子集（ISO 14229）

| SID | 服务 | 说明 |
|---|---|---|
| `10` | 诊断会话控制 | 默认 / 编程 / 扩展会话 |
| `11` | ECU 复位 | 受会话限制 |
| `22` | 按标识符读数据 | DID `F1A0` 返回上一条 ISO-TP 包的长度与 CRC16 |
| `27` | 安全访问 | 种子-密钥，连续错误计数与锁定 |
| `28` | 通信控制 | 停/开周期报文 |
| `31` | 例程控制 | 擦除暂存区 / 校验镜像（分步回 `0x78` 保活） |
| `34` | 请求下载 | 协商块长 258 = 2 + 256 |
| `36` | 传输数据 | 块序号校验、写 W25Q64、累加 CRC-A |
| `37` | 退出传输 | 校验 CRC-A、写就绪头、置升级标志 |
| `3E` | 保活 | 支持抑制位 |
| `85` | 故障记录开关 | — |

S3 定时器由**任何请求**重置（ISO 14229 要求），而不是只有 `0x10` / `0x3E`。

## 4. CAN-OTA

```
PC ──TCP 5000──> 网关 ──CAN 0x2E0──> 记录仪
                                     ├ 34 请求下载（协商块长）
                                     ├ 36 × 315 块（每块 258 B）
                                     └ 37 退出传输（CRC-A 校验）
                                            │
                                            ├ 写 W25Q64 暂存区（magic 最后写）
                                            └ 置升级标志 → 复位 → Boot 装载
```

- 整包 80,504 B ／ 315 块 × 256 B
- **两级 CRC**：CRC-A 逐块校验传输完整性，CRC-B 整包校验落盘内容
- 先落 W25Q64 暂存区，整包校验通过才写内部 Flash；传输期断电旧固件照常启动
- 实测 **23 s / 3.4 KB/s**（500 kbps 总线，停等协议）

## 7. 自动化测试

配套工具在 `tools/`（Python 3，需 `pyserial`）。

```bash
python tools/run_all.py            # 41 个用例，约 35 秒
python tools/run_all.py --list     # 看有哪些组
python tools/run_all.py --only sec # 只跑一组
python tools/download_test.py      # 315 块 OTA 压测
python tools/soak72.py --hours 72  # 长稳观察（只走网络，不占串口）
```

| 组 | 用例数 | 内容 |
|---|---|---|
| ISO-TP | 5 | 单帧 / 首帧连续帧 / 超缓冲拒收 / 流控计数 |
| UDS 会话与保活 | 11 | 会话切换、S3 超时、长度与子功能参数校验 |
| UDS 安全访问 | 7 | 种子-密钥、错误锁定、未解锁拒绝 |
| UDS 通信控制 | 10 | 停/开周期报文、抑制位 |
| UDS 例程控制 | 8 | 擦除暂存区、镜像校验、未解锁拒绝 |

几个刻意的设计：

- **以子进程退出码为主判据**，PASS 行数只作参考 —— 早期版本「脚本 `exit 1` 但打印了全 PASS」会判绿（假绿）。
- ISO-TP 组的断言**不看设备串口打了什么**，而是读 UDS `0x22`（DID `F1A0`）拿「上一条包的长度 + CRC」。这样 dump 可以长期关闭，回归也不再占用串口。
- `len=300` 用例除了验证「超过缓冲必须拒收」，还断言网关侧 `cfd`（被丢弃的连续帧）计数上升 —— 证明确实走进了 OVFLW 丢弃分支，而不是碰巧没收到。

### 已知测试环境约束

`download_test.py` 结束时暂存区会留一份完整镜像与就绪头。下一次请求升级时 Boot 会先装载它再重启，因此**紧接着的那次串口烧写会失败一次**（E 命令落在装载窗口内），重跑即可。Boot 本身逻辑正确：装载前已把就绪头清成 `STAGE_NONE`。

## 10. 踩过的坑

这一节记的是定位过程，不是最终代码。每条按「现象 → 怎么找到的 → 根因 → 解法」写，
因为**系统是怎么被验证的**，比最终代码更能说明问题。

### 10.1 CAN-OTA 固定在第 8 / 20 块失败，回 `7F 36 73`

> 设计权衡已经写在第 2 节，这里只记当时是怎么定位到的。

**现象**：CAN-OTA 传到第 8 块和第 20 块必定失败，NRC `0x73`（块序号错）。

**怎么找到的**：`0x73` 的意思是"收到的块号不对"，说明有块丢了。对比发现
**三帧交替时一次过，改成四帧同拍就必挂**——变量只有"同一拍要几个邮箱"。

**根因在对端节点**：bxCAN 只有 **3 个发送邮箱**，而对端一拍要发 4 帧遥测。第 4 帧去要邮箱时
三个都被占着，网关发出的诊断请求排不上队，响应超时导致整块重传。

遥测丢一帧只是曲线少个点；**诊断丢一帧 PC 得整块重传**。两者代价差几个数量级，
所以必须显式定优先级。

**解法在对端节点**：诊断帧发送前先抢占一个遥测邮箱（撤掉一帧周期重发、丢了不心疼的帧）。

> 这部分实现属于 **F103 记录仪仓库**，本仓库不贴对端代码，只记录现象与结论。

**结果**：315 块 / 21.3 s / 3.7 KB/s，全部 PASS。

### 10.2 W5500 在 0.656 MHz 下静默丢弃命令

**现象**：能读对 `VERSIONR`（`0x04`），但写 `Sn_CR` 开 socket 一律不生效，
96 次尝试 96 次失败，没有任何报错。

**怎么找到的**：读方向正常、写方向全废，说明不是接线问题。把 SCLK 从 0.656 MHz
提到 21 MHz 后立刻好转。

**教训**：直觉上"SPI 太快会出错"，实际上**太慢也会**。W5500 对命令字节有超时窗口，
SCLK 太慢时命令还没发完就被芯片判失效。定位这类问题，速率要作为独立变量扫一遍。

### 10.3 读两字节寄存器得到 0x0710（应为 0x07D0）

**现象**：`RTR`（重传时间）默认值读回来是 `0x0710`，但手册写 `0x07D0`。
错得很规整——像是两个字节各错了几位。

**怎么找到的**：换成逐字节 `HAL_SPI_TransmitReceive()` 发 `0xFF` 占位就对了，
用 `HAL_SPI_Receive()` 就错。说明问题在"读的时候发什么占位字节"，不在 W5500。

**顺带发现另一件事**：CS 拉高后还芯片内部要收尾时间。把那段空转省掉之后，
`RCR` 连读 10 次有 2 次读成 `0x10`（应为 `0x08`）。所以**CS 拉高后必须空转几拍再返回**。

**教训**：SPI 从机的寄存器读，本质是"发地址、同时收数据"。占位字节发什么、
CS 什么时候放，都会体现在数据上。

### 10.4 传感器坏值不要硬算

**现象**：F103 节点在传感器读失败时发 `0xFFFF`（湿度）或 `0x8000`（温度）。
网关直接把 16 位当数值显示，于是出现 `6553.5%` 这种数，宽度还把 240 像素的屏顶出去。

**解法**：不判"等于不等于哨兵值"，而是**按物理量程判**：

```c
/* 判据按物理量程：DS18B20 -55~125 度，湿度 0~100%，气压 300~1100 hPa
 * 气压多判一个下界：0 多半是链路上没数据，不是真的没气压 */
t_bad = (uint8_t)(((tv < -5500) || (tv > 12500)) ? 1u : 0u);
...
if (hv > 1000u) { lv_bar_set_value(s_bar_humi, 0, LV_ANIM_OFF);
                  lv_label_set_text(s_lab_humi_val, "--.-%"); }
```

**为什么量程判定比哨兵判定好**：哨兵值只有一个，而"链路没接"、"上位机没发"、
"字段错位"都会产生量程外的值。按量程判能一并兜住，而且不需要协议约定。

### 10.5 注释在一次编码往返里被整体毁掉

**现象**：三个文件（`main.c`、`w5500_port.c`、`w5500_port.h`）的中文注释变成
`锟斤拷` 或者 `U+FFFD`，但**代码照常编译、功能照常工作**——所以很久没被发现。

**更隐蔽的一种**：GBK 里有些汉字的第二字节正好是 `0x5C`（反斜杠）。它落在
`//` 注释行末时会**吃掉换行符**，把下一行代码并进注释，编译时报出
`a storage class may not be specified here` 这种和代码完全无关的错误。

**解法**：所有源码读写走同一个编码层（BOM → 纯 ASCII → 严格 UTF-8 → 严格 GBK），
写回时保持原编码与原换行风格，改完做**读→原样写回→SHA256 比对**。

**教训**：看到"莫名其妙的语法错误"，第一反应应该是查文件编码，不是查代码逻辑。

**补记（2026-11-25）**：这些注释的原文已经不可恢复——备份和 git 历史里同样是坏的
（有一个备份看着"没有乱码"，其实只是把汉字换成了 `U+FFFD`，信息一样丢了）。
最终是**逐个读周边代码重写**的。为了证明"只改了注释"，写了一个 C 注释剥离器
（正确跳过字符串与字符字面量），比对改前改后的 token 序列：2914 vs 2914，完全一致。
