# 76 - 通信协议契约（双板 CAN 网关）- 2026-11-21

> **这份文档的地位**：F103 记录仪和 F407 网关之间所有通信格式的**唯一真相**。
>
> **规矩**：改帧格式 = 先改本文档，再改两边的代码，最后重跑验证。
> 代码和文档不一致时，**以文档为准，代码是 bug**。
>
> 为什么要有这份东西：2026-11-21 发现在 SD 卡 CSV 加了 `sonar` 列之后，串口回显忘了同步，
> 原因是"同一份契约在多个地方各写一份"。本文档就是为了消除这种情况。

---

## 一、术语与约定

| 术语 | 含义 |
|---|---|
| **记录仪** | F103 工业记录仪，发数据的一方 |
| **网关** | F407 CAN 网关，收数据的一方 |
| **DATA 帧** | 遥测数据帧 |
| **STAT 帧** | 状态心跳帧 |
| **LE** | 小端（Little Endian），低字节在前 |

### 字节序：统一小端

**所有多字节字段一律小端，低字节在前。**

理由：两颗 MCU 都是 ARM Cortex-M，原生小端，直接 `memcpy` 即可，不需要转换。

**注意**：Modbus 默认是**大端**。将来做 Modbus 网关时，寄存器层面要做字节交换，这是两回事，不要混。

### 数值单位：全项目统一

| 物理量 | 存储单位 | 换算 | 示例 |
|---|---|---|---|
| 温度 | 0.01 °C | ÷100 | `2287` = 22.87 °C |
| 湿度 | **0.1 %RH** | **÷10** | `314` = 31.4 %RH |
| 压力 | Pa | ÷100 得 hPa | `102271` = 1022.71 hPa |
| RTC 时间 | unix 秒 | — | `1795164037` |
| tick | 毫秒 | — | `1471401` |

**湿度是 0.1 不是 0.01**，这是历史遗留（DHT22 原生格式就是 0~1000 表示 0.0~100.0%）。
2026-11-20 曾因此出过显示小十倍的 bug，记在这里防止再犯。

## 二、物理层

### CAN（主通道，收发器到货后启用）

| 项目 | 值 |
|---|---|
| CAN 外设 | CAN1 |
| 引脚 | 记录仪 PB9(TX)/PB8(RX)，网关 PB9(TX)/PB8(RX) |
| 波特率 | 500 kbps |
| 记录仪位时序 | APB1 36 MHz / 预分频 4 / 1+BS1 13+BS2 4 = 18 tq / 采样点 77.8% |
| 网关位时序 | APB1 42 MHz / 预分频 4 / 1+BS1 16+BS2 4 = 21 tq / 采样点 80.95% |
| 终端电阻 | 两端各 120 Ω（在收发器板上） |
| 帧类型 | 标准帧（11 位 ID），数据帧 |

### I2C（临时通道，CAN 未通时使用）

| 项目 | 值 |
|---|---|
| 引脚 | 记录仪 PB8(SCL)/PB9(SDA)，网关 PB8(SCL)/PB9(SDA) |
| 速率 | 50 kHz |
| 网关地址 | 0x50（7 位），OAR1 要填 `0x50 << 1` |
| 接线 | **直连**：SCL 对 SCL、SDA 对 SDA（不是交叉） |
| 上拉 | 网关内部 40 kΩ |

**注意**：PB8/PB9 是 CAN 和 I2C 的共用引脚，二选一，不能同时启用。

## 三、CAN 帧 ID 分配

ID 越小优先级越高（CAN 仲裁规则），所以实时性要求高的排前面。

| ID | 名称 | 方向 | 频率 | 用途 |
|---|---|---|---|---|
| **0x080** | ALARM | 记录仪 → 网关 | 事件触发 | 告警，最高优先级 |
| **0x101** | DATA | 记录仪 → 网关 | 10 Hz | 遥测数据 |
| **0x102** | STAT | 记录仪 → 网关 | 10 Hz | 序号 + 状态 + 时间 |
| **0x201** | CMD | 网关 → 记录仪 | 按需 | 配置命令 |
| **0x301** | ACK | 记录仪 → 网关 | 按需 | 命令应答 |

**为什么 0x080 排最前**：告警要抢占数据帧。CAN 硬件仲裁会自动让 ID 小的先发，不需要软件干预。

## 四、逐帧定义

### 4.1 0x101 DATA —— 遥测数据

**DLC = 8**

| 字节 | 字段 | 类型 | 单位 | 说明 |
|---|---|---|---|---|
| 0-1 | `temp_ds` | int16 | 0.01 °C | DS18B20，范围 -55.00~125.00 |
| 2-3 | `humi` | uint16 | 0.1 %RH | DHT22，范围 0~1000 |
| 4-7 | `press_pa` | uint32 | Pa | BMP280，范围 30000~110000 |

**打包示例（记录仪侧）：**

```c
uint8_t d[8];
uint32_t p_pa = rec.press / 10u;    /* 记录仪内部 ×10 Pa，转成 Pa */

d[0] = (uint8_t)((uint16_t)rec.temp_ds & 0xFFu);
d[1] = (uint8_t)(((uint16_t)rec.temp_ds >> 8) & 0xFFu);
d[2] = (uint8_t)(rec.humi & 0xFFu);
d[3] = (uint8_t)((rec.humi >> 8) & 0xFFu);
d[4] = (uint8_t)(p_pa & 0xFFu);
d[5] = (uint8_t)((p_pa >> 8) & 0xFFu);
d[6] = (uint8_t)((p_pa >> 16) & 0xFFu);
d[7] = (uint8_t)((p_pa >> 24) & 0xFFu);
```

### 4.2 0x102 STAT —— 状态心跳

**DLC = 8，和 DATA 帧同频发送（10 Hz），成对出现。**

| 字节 | 字段 | 类型 | 单位 | 说明 |
|---|---|---|---|---|
| 0-1 | `seq` | uint16 | — | 帧序号，每发一帧 +1，65535 后回绕 |
| 2 | `status` | uint8 | 位域 | 见 4.4 |
| 3 | `proto_ver` | uint8 | — | 协议版本，当前为 1 |
| 4-7 | `rtc` | uint32 | unix 秒 | 记录仪采集时刻的时间戳 |

**为什么分开成两帧**：
- DATA 帧 8 字节被三个物理量占满了（2+2+4），塞不下 seq
- STAT 帧同频发，网关按 seq 连续性判断丢帧
- 总线负载：20 帧/秒 × 约 130 位 = 2600 位/秒，500 kbps 下只占 **0.5%**，完全不用担心

### 4.3 0x080 ALARM —— 告警事件

**DLC = 8，只在状态变化时发，不发心跳。**

| 字节 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | `alarm_code` | uint8 | 告警类型，见下表 |
| 1 | `severity` | uint8 | 0=信息 1=警告 2=严重 3=致命 |
| 2-3 | `param` | uint16 | 告警关联数值（如超限值） |
| 4-7 | `rtc` | uint32 | 发生时刻 |

**告警类型表（当前定义）：**

| 码 | 含义 | 典型 severity |
|---|---|---|
| 1 | 温度超上限 | 2 |
| 2 | 温度超下限 | 2 |
| 3 | 压力超范围 | 2 |
| 4 | 湿度传感器故障 | 1 |
| 5 | SD 卡写失败 | 2 |
| 6 | SD 卡拔出 | 3 |
| 7 | 数据丢弃（队列满） | 2 |
| 8 | RTC 掉电重置 | 1 |

**同一条告警不重复发**：状态进入时发一次，恢复时不发（网关靠 status 位判断恢复）。

### 4.4 status 字节位定义

| 位 | 名称 | 含义 | 置 1 表示 |
|---|---|---|---|
| bit0 | `ST_TEMP` | DS18B20 | 读数正常 |
| bit1 | `ST_HUMI` | DHT22 | 读数正常 |
| bit2 | `ST_PRESS` | BMP280 | 读数正常 |
| bit3 | `ST_IMU` | MPU6050 | 读数正常 |
| bit4 | `ST_SD` | SD 卡 | 挂载正常、可写 |
| bit5 | `ST_RTC` | RTC | 时间有效 |
| bit6 | `ST_ACQ` | 采集任务 | 正在按 10 Hz 运行 |
| bit7 | `ST_BACKFILL` | 补传中 | 这帧数据来自缓存补传，不是实时 |

**bit7 的意义**：SD 卡拔出时数据进 W25 缓存，恢复后补传。网关看到 bit7=1 就知道"这是历史数据"，可以用 rtc 字段还原时间线。

### 4.5 0x201 CMD —— 配置命令（网关 → 记录仪）

**DLC = 8，按需发送。**

| 字节 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | `cmd` | uint8 | 命令码，见下表 |
| 1-7 | `param` | uint8[7] | 参数，按命令解释 |

| 命令码 | 含义 | 参数 |
|---|---|---|
| 1 | 设置采集周期 | `param[0]` = 周期，单位 10 ms |
| 2 | 设置 RTC | `param[0-3]` = unix 秒（LE） |
| 3 | 清空告警锁存 | 无 |
| 4 | 强制写盘 | 无 |
| 5 | 重启 | 无 |
| 0xFF | 查询版本 | 无 |

### 4.6 0x301 ACK —— 命令应答

**DLC = 8**

| 字节 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | `cmd` | uint8 | 应答的命令码（和 CMD 对应） |
| 1 | `result` | uint8 | 见下表 |
| 2-7 | `rsv` | uint8[6] | 保留，填 0 |

| result | 含义 |
|---|---|
| 0 | 成功 |
| 1 | 参数非法 |
| 2 | 忙，稍后重试 |
| 3 | 不支持该命令 |

**超时规则**：网关发出 CMD 后 100 ms 内没收到对应 ACK，重发最多 3 次；3 次都失败则报错。

## 五、序号机制

### 记录仪侧

```c
static uint16_t s_seq = 0u;

/* 每发一帧 STAT，序号 +1 */
s_seq++;
d[0] = (uint8_t)(s_seq & 0xFFu);
d[1] = (uint8_t)((s_seq >> 8) & 0xFFu);
```

**序号只在 STAT 帧里，和 DATA 帧成对发送，所以序号连续性等价于 DATA 帧连续性。**

### 网关侧丢帧检测

```c
static uint16_t s_last_seq = 0u;
static uint8_t  s_seq_valid = 0u;
static uint32_t s_lost_total = 0u;

uint16_t seq = (uint16_t)(d[0] | ((uint16_t)d[1] << 8));

if (s_seq_valid != 0u)
{
    /* 用无符号减法自动处理 65535 回绕，不要写成 if (seq > last) */
    uint16_t delta = (uint16_t)(seq - s_last_seq);

    if (delta != 1u)
    {
        s_lost_total += (uint32_t)(delta - 1u);
    }
}

s_last_seq  = seq;
s_seq_valid = 1u;
```

**回绕处理的关键**：`(uint16_t)(seq - last_seq)` 在回绕时天然得到正确的小差值。
如果写成 `if (seq > last_seq)` 判断，回绕那一刻会误判成"丢了 65534 帧"。

### 丢帧率显示

网关屏幕上显示：

```
LOST 3 / 12580 (0.02%)
```

**这就是可量化的可靠性指标**，和 SD 那块"SD: W avg/max"一个性质。

## 六、时间戳规则

**网关必须用记录仪发来的 `rtc` 字段作为数据时间，不能用自己收到的时间。**

理由：采集时刻在记录仪那一端，传输有延迟（CAN 帧传输约 130 µs，加上排队可能几百 µs）。用收到时间打戳会引入误差。

**如果 rtc 无效**（记录仪 status 的 `ST_RTC` 位为 0）：
- 记录仪填 0
- 网关收到 rtc=0 时不写数据库，只显示"时间无效"

## 七、异常处理

| 异常 | 处理 | 计数 |
|---|---|---|
| 收到未知 ID | 丢弃 | `g_can_unknown_id` |
| DLC 不等于 8 | 丢弃 | `g_can_bad_dlc` |
| 版本号不认识 | 按最低版本解析，置告警 | `g_can_bad_ver` |
| 序号不连续 | 累加丢帧数，不丢弃数据 | `g_lost_total` |
| 超过 3 秒无 STAT 帧 | 显示"链路断开" | `g_link_down_ms` |
| CAN bus-off | 自动恢复（ABOM 已开），计数 | `g_can_busoff_cnt` |
| I2C CRC 错 | 丢弃该帧 | `g_i2c_crc_err` |

### 关于校验

| 通道 | 校验 | 说明 |
|---|---|---|
| **CAN** | 硬件 CRC15 | CAN 外设自动生成和校验，应用层不需要再加 |
| **I2C** | **应用层 CRC16** | I2C 的 ACK 只证明"收到了字节"，不证明"内容对"，必须自己做 |
| **串口** | 行尾 crc 字段 | 调试用，见 SD 卡 CSV 的 CRC16/KERMIT |

**I2C 的 ACK 不等于数据正确** —— 线上一抖动导致某位翻转，从机照样回 ACK。这是 I2C 和 CAN 的本质差别。

## 八、版本兼容规则

### 版本号位置

`0x102` STAT 帧的第 3 字节 `proto_ver`。

### 规则

| 改动类型 | 要不要升版本 | 兼容性 |
|---|---|---|
| 新增一个 ID | 不需要 | 老网关忽略未知 ID |
| 在帧尾加字段（空间够） | 需要 | 老网关按老长度解析 |
| 修改已有字段含义或位置 | **必须升** | 老网关全部需要更新 |
| 删除 ID | 不需要 | 老网关忽略 |

### 版本不匹配时

网关检测 `proto_ver > 本端支持的最高版本`：
- 记录日志 `g_can_bad_ver++`
- 在屏幕上显示版本警告
- **按已知字段尽量解析**（不丢弃数据）

## 九、一致性检查清单

**这是本文档存在的核心目的。**

任何一次帧格式改动，必须检查以下 **5 处** 全部同步：

| # | 位置 | 文件 | 检查什么 |
|---|---|---|---|
| 1 | **本文档** | 学习笔记 76 | 帧定义表 |
| 2 | 记录仪打包 | `工业记录仪\User\can_tx.c` | `d[0]..d[7]` 的赋值顺序 |
| 3 | 记录仪串口回显 | `工业记录仪\User\freertos_demo.c` | `Serial_Printf("REC,...")` 的字段 |
| 4 | 网关解包 | `CAN网关\Core\Src\main.c` | `Bridge_Parse()` 的偏移 |
| 5 | 网关显示 | `CAN网关\Core\Src\main.c` | `lcd` / `lv_label` 的显示 |
| 6 | SD 卡 CSV | `工业记录仪\User\task_sd.c` | `SD_CSV_HDR[]` 和 task_PROC 的 sprintf |

**已知未对齐项（待修）**：

- 串口 REC 回显缺 `sonar` 字段（CSV 有 17 列，串口只有 15 个数据字段 + crc）

### 怎么防止再漏

**推荐做法**：把字段表写成一处宏，两边都用它展开。示例：

```c
/* 字段表：唯一来源 */
#define DATA_FIELDS(X) \
    X(temp_ds, int16,  0.01, "C")   \
    X(humi,    uint16, 0.1,  "%")   \
    X(press,   uint32, 1,   "Pa")

/* 记录仪打包 */
#define PACK(name, type, scale, unit) /* ... */
DATA_FIELDS(PACK)

/* 网关解包 */
#define UNPACK(name, type, scale, unit) /* ... */
DATA_FIELDS(UNPACK)
```

**但**：已通过 72 小时验证的代码重构风险大于收益。
**建议**：新写的协议（Modbus 寄存器映射）用这个思路，老代码保持现状 + 靠本文档约束。

## 十、验证方法

**每一条改动都有可量化的验收标准。**

| 验证项 | 方法 | 合格标准 |
|---|---|---|
| **序号连续性** | 连续收 10000 帧，看丢帧计数 | `LOST = 0` |
| **数据正确性** | 同时抓记录仪串口和网关显示，逐项对比 | 三个量完全一致 |
| **状态位** | 拔掉 DHT22，观察 bit1 | 30 秒内变 0 |
| **告警触发** | 用热风枪吹 DS18B20 超过阈值 | 收到 0x080，severity=2 |
| **时钟有效性** | 记录仪断电重启后观察 | ST_RTC 位在 RTC 初始化后变 1 |
| **CAN bus-off 恢复** | 短接 CANH/CANL 再断开 | busoff 计数 +1，之后自动恢复 |
| **I2C CRC** | 人为改错 1 字节（临时改代码） | 该帧被丢弃，`g_i2c_crc_err` +1 |
| **长时间稳定性** | 连续跑 8 小时 | 丢帧率 < 0.01%，无 bus-off |

## 附：为什么这份文档要这么写

**工业上把这种东西叫 "Interface Control Document"（接口控制文档，ICD）。**

**任何两个设备、两个模块、两个团队对接，都会先签一份 ICD。**

**它的作用不是"记录做了什么"，而是：**

1. **唯一真相** —— 出了分歧以它为准，不靠"我记得是这样的"
2. **变更控制** —— 改之前就知道会影响哪几处
3. **可交接** —— 换个人接手，看文档就懂
4. **可测试** —— 每条定义都对应可执行的验收标准

**你现在有了这份文档，就具备了"能被别人接手"的条件** —— 这在面试里是个很实的加分点。
