## 0. 一句话

把"给 F103 加一条 CAN 升级通道"这件事，做成 **ISO-TP 传输层 + UDS 诊断服务子集**，
复用已经验证过的 W25Q64 暂存区与 Boot 自愈体系，**Bootloader 一行不改**。

## 1. 工业界怎么做

### 1.1 三个流派（都在 CAN 上传固件，规则不同）

| 流派 | 标准 | 传输层怎么分块 | 典型场景 |
|---|---|---|---|
| 汽车电子 | UDS（ISO 14229）+ ISO-TP（ISO 15765-2） | ISO-TP 分帧（SF/FF/CF/FC）+ UDS `34/36/37` | ECU 刷写、OTA |
| 工控 / 运动控制 | CANopen（CiA 301） | SDO 块传输（block transfer） | 伺服、PLC、远程 IO |
| 商用车 / 工程机械 | SAE J1939 | 传输协议 TP（BAM 广播 / CMDT 点对点） | 发动机、农机、船舶 |

CANopen 侧有成熟的标准 Bootloader 产品，固件走 SDO 块传输；J1939 侧靠 BAM/CMDT 传大包。
ST 自己也有 CAN IAP 应用笔记（AN3154）。这三套做的事相同，只是分块和握手的规则不同。

### 1.2 汽车 UDS 刷写 = 严格三段式

不是"发个 bin 就完事"，而是：

```
【预编程】3E 保活 → 10 03 扩展会话 → 85 关 DTC → 28 关非诊断报文（让总线安静）
【主编程】10 02 编程会话 → 27 Seed-Key → 2E 写指纹 → 31 擦除
          → 34 请求下载（协商块长）→ 36 传数据 × N → 37 退出
          → 31 校验完整性 → 11 复位
【后编程】10 03 → 28 开 → 85 开 → 27 → 2E → 10 01
```

几个必须知道的细节：

1. **`10 02` 不能由 App 直接回肯定响应**。正确做法是 App 回 `7F 10 78`（NRC 0x78 正在处理），
   跳 Boot，由 **Boot** 回 `50 02`。
2. **`0x36` 的 blockSequenceCounter 是 1 字节**，从 `0x01` 开始，到 `0xFF` 之后**绕回 `0x00`**
   （不是 `0x01`）。靠它检测丢块 / 重复块 / 乱序块。
3. **长耗时操作要先回 `0x78`**。`0x36` 里要做 Flash 擦除/编程，可能超过 P2\*（通常 5 s），
   所以先回 `NRC 0x78`，干完再回最终响应。这条直接决定我们的擦暂存区要不要单独握手。
4. **`0x34` 会协商 `maxNumberOfBlockLength`**，Tester 后续每块长度必须 ≤ 这个值。
5. **`0x37` 之后必须再发 `31 01` 校验完整性**，否则新固件可能无效。
6. **Bootloader 都留一个上电窗口**（常见 100 ms ~ 2 s，典型 200 ms），窗口内收到请求就不跳 App。
   目的就是"App 半死不活也能被覆盖掉"。
7. **`0x27` 是种子-密钥挑战响应**：种子有效期常见 5 s，连续 3 次错密钥锁 10 分钟。

### 1.3 MCU 侧那一半：Flash 怎么安全换

工业界不叫"暂存区"，叫 **slot**：

- **MCUboot**：`[Bootloader | Slot 0 | Slot 1 | Scratch]`，六种 swap 策略，
  掉电安全靠"把 swap 进度写进 Flash，下次开机接着换"。
- **ESP-IDF**：`ota_0` / `ota_1` + `otadata` 分区，状态机
  `NEW → PENDING_VERIFY → VALID / INVALID / ABORTED`，防回滚靠 eFuse 里的 security version。
- **A/B 双分区**：新固件写 B 区、校验通过才切换启动标志，失败继续跑 A 区。

## 3. 要建的：ISO-TP + UDS 子集

### 3.1 分层

```
    PC 上位机（UDS Tester）
       │  TCP 到 F407:9000（自定义长事务通道）
       ▼
    F407 网关  ── UDS 转发（透明，只看 ID）──►  CAN 500 kbps
                                                  │  ISO 15765-2 分帧
                                                  ▼
                                        F103 APP：UDS 服务端
                                          · 0x34 协商块长
                                          · 0x36 每块写 W25 + 累加 CRC
                                          · 0x37 收尾 → 置暂存头 READY → 复位
                                                  │
                                                  ▼
                                        F103 Boot：现有逻辑自己装（零改动）
```

### 3.2 CAN ID 分配

沿用现有编号规律（`0x2xx` 网关→记录仪，`0x3xx` 记录仪→网关）：

| ID | 方向 | 用途 |
|---|---|---|
| `0x2E0` | 网关 → 记录仪 | UDS 物理请求（ISO-TP） |
| `0x3E0` | 记录仪 → 网关 | UDS 物理响应（ISO-TP） |

现有 `0x201/0x301`（CMD/ACK）保持原义，不用来传固件。

### 3.3 ISO-TP 帧格式（经典 CAN，8 字节）

| 类型 | 第一字节 | 之后 | 单帧可载数据 |
|---|---|---|---|
| SF 单帧 | `0x0L`（L = 1~7） | data[L] | ≤ 7 B |
| FF 首帧 | `0x1` + 长度高 4 位 | 长度低 8 位 + data[6] | 6 B |
| CF 连续帧 | `0x2` + SN（0~15） | data[7] | 7 B |
| FC 流控 | `0x3` + FS（0=CTS/1=WAIT/2=OVFLW） | BS、STmin、0… | — |

### 3.4 参数选择与理由

| 参数 | 取值 | 理由 |
|---|---|---|
| `maxNumberOfBlockLength` | **258**（= 2 + 256） | 256 B 正好一个 W25Q64 页，写一次是一页；2 B 是 `0x36` 的 SID + blockSeq |
| `BS`（BlockSize） | **8** | 每 8 个 CF 让接收方回一次 FC，给它一个"我忙"的说话机会；取 0 就完全失去节流能力 |
| `STmin` | **0** | F103 收一帧只是中断里拷 7 字节，不需要间隔。取 2 ms 会把吞吐压到 3.6 KB/s，比串口还慢 |
| `N_Bs` / `N_Cr` 超时 | **1000 ms** | ISO-TP 通用值 |
| `P2` / `P2*` | 50 ms / 5000 ms | UDS 通用值；我们擦暂存区会超 P2\*，必须走 `0x78` |
| S3（会话保持） | 5000 ms | 无 `3E` 则退回默认会话 |

### 3.5 UDS 服务清单（只做这 10 个）

| SID | 服务 | 子功能 | 我们拿它干什么 |
|---|---|---|---|
| `0x10` | DiagnosticSessionControl | 01 默认 / 02 编程 | 进/出编程会话 |
| `0x11` | ECUReset | 01 硬复位 | 装完后复位 |
| `0x27` | SecurityAccess | 01 求种子 / 02 送密钥 | 防未授权刷写 |
| `0x28` | CommunicationControl | 00 开 / 03 关 | 停 `0x101`/`0x102` 的 10 Hz 上报，让总线安静 |
| `0x3E` | TesterPresent | 00 | 保活，喂 S3 定时器 |
| `0x85` | ControlDTCSetting | 01 开 / 02 关 | 对应 `Event_LogFail`，刷写期间别记假故障 |
| `0x31` | RoutineControl | 01 擦除 / 01 校验 | 擦 27 个扇区；校验 CRC |
| `0x34` | RequestDownload | — | 协商 `maxNumberOfBlockLength` |
| `0x36` | TransferData | — | 传 256 B / 块，带 blockSeq |
| `0x37` | RequestTransferExit | — | 收尾、置暂存头 READY |

**只做这些**：`19/14`（故障码）、`22/2E`（DID 读写）对这块板没意义，不做。

**NRC 要实现的**：`0x10 0x11 0x12 0x13 0x22 0x24 0x31 0x33 0x35 0x36 0x73 0x78 0x7F`。
其中 `0x73`（wrongBlockSequenceCounter）和 `0x78`（responsePending）是这套协议的"味道"所在，
不能省。

### 3.6 一次升级的完整时序

```
PC/F407                              F103 APP
  │  3E 00                            │
  ├──────────────────────────────────►│  50 3E
  │  10 03                            │
  ├──────────────────────────────────►│  50 03   （扩展会话）
  │  85 02                             │
  ├──────────────────────────────────►│  C5 02   （关 DTC）
  │  28 03                             │
  ├──────────────────────────────────►│  68 03   （停 0x101/0x102）
  │  10 02                             │
  ├──────────────────────────────────►│  50 02   （本次偏差：App 直接肯定，理由见 §4）
  │  27 01                             │
  ├──────────────────────────────────►│  67 01 <seed[4]>
  │  27 02 <key[4]>                    │
  ├──────────────────────────────────►│  67 02
  │  31 01 FF00                        │
  ├──────────────────────────────────►│  7F 31 78  ← 先回"我在擦"
  │                                    │  擦 27 个 4 KB 扇区（1.2~10.8 s）

  ├──────────────────────────────────►│  51 01 → 复位
```

## 4. 与工业界的三处故意偏差（面试要能讲清楚）

### 偏差一：`10 02` 由 App 回肯定响应

工业上必须 App 回 `7F 10 78`、跳 Boot、由 Boot 回 `50 02`。

**我们为什么不这么干**：Boot 现在 11,772 B / 16,384 B，只剩 **4,612 B**。
塞 CAN 驱动（`stm32f10x_can.c` 编译后约 4~6 KB）加接收状态机放不下。
而我们的 Boot 已经有"暂存区 + 开机自愈"这套等价机制：App 收完写暂存区、置 READY、复位，
Boot 开机看到 READY 就自己装。

**代价**：如果 App 已经坏到跑不起来，CAN 这条路就没了 —— 所以**串口必须保留**。
这正好是"手机 OTA + 接电脑线刷"的分工。

### 偏差二：single slot + 外部 secondary slot，不是 A/B 双分区

F103 只有 128 KB Flash、App 占 108 KB，**装不下两份**。
所以用 W25Q64 当 secondary slot。这在 MCUboot 的术语里叫
"secondary slot on external flash"，是正规做法，不是土办法。

### 偏差三：不做 FlashDriver 下发

OEM 不允许 ECU 固件里带擦写 Flash 的代码，所以要现场把 FlashDriver 下发到 RAM 再调。
我们的 Boot 里本来就有擦写代码，做这个纯属自找麻烦。

## 5. 可靠性设计

| 故障 | 处理 |
|---|---|
| 丢 CF 帧 | SN 不连续 → 接收方回 `NRC 0x73`，Tester 重发该块 |
| 丢整块 | 块级超时 → Tester 重发该块；重试 3 次失败则终止 |
| 擦除超时 | `NRC 0x78` 先回，Tester 放宽该步超时（15 s） |
| 升级中断电 | 暂存头 magic 最后补 → 半截镜像当没有；App 仍有效照常开机 |
| 搬移中断电 | 第 0 页最后写 → 下次开机重搬 |
| App 装坏 | 金副本回滚（IWDG 复位也是判据） |
| 装低版本 | `img_min_ver` 拒绝 |
| **传输错** | **CRC-A**：F103 收到每块就累加，对不上 PC 给的立刻终止 |
| **存储错** | **CRC-B**：Boot 从 W25 读出来再算一遍 |

**两个 CRC 管两件不同的事**，这是整段设计里最容易讲出深度的地方：

```
CRC-A（传输层）防"总线位翻转 / 丢帧 / 重帧"
CRC-B（存储层）防"W25 写坏 / 搬的时候掉电"
```

现有 `Up_StageCrc()` 只做 CRC-B。**必须**在写 W25 之前自己再算一遍 CRC-A，
否则总线把某个字节翻反了、又恰好写进 W25，两边算出来是一样的。

## 6. 上电窗口（已实现，2026-11-23）

`Boot/main.c` 新增 `Boot_WaitWindow(300u)`：Boot 走到"没人请求升级 + App 有效"这一步时，
先听 300 ms 串口。

- 收到 `Z` → 回 `FAIL cmd`（PC 探针靠这句认 Boot）→ 进升级模式
- 收到 `U` → 进升级模式
- 收到 `C` → 直接跳 App
- 其它字节丢掉（防噪声把板子一直拖在升级模式）
- 真被误触发也不怕：升级模式空闲 25 秒会自己跳回 App

**成本**：整个 Boot 的 ROM 从 11,524 → **11,772 B**（+248 B），16 KB 里还剩 **4,612 B**。

**已知竞态**：开机 300 ms 内跑 `flash_app.py`，探针会收到 `FAIL cmd` 而误判"对面是 Boot"。
规避办法：开机之后再跑工具（正常情况下板子早就在 App 里了）。

## 7. 验收清单

| # | 验什么 | 判据 |
|---|---|---|
| 1 | ISO-TP 分帧正确 | 本机没有 CAN 分析仪（`Get-PnpDevice` 只有 CH340 + ST-Link），**只能经 F407 转发**：PC → TCP → F407 → CAN，由 PC 脚本逐帧核对 PCI 字节 |
| 2 | 块序号检测 | 故意跳一个 blockSeq，F103 必须回 `7F 36 73` |
| 3 | `0x78` 生效 | 擦除期间 Tester 收到 `7F 31 78`，不超时 |
| 4 | 能力协商 | `34` 的响应里 `maxBlockLen=258`，Tester 每块不超过它 |
| 5 | 断点续传 | 传到一半拔电，重启后 `31 01 0202` 报 CRC 失败；Tester 从头重发能成 |
| 6 | 掉电安全 | 擦除中、传一半、搬移中，各随机断电 5 次，10/10 能起来 |
| 7 | 串口仍是救砖通道 | 故意刷一个坏镜像，串口 `Z` → `FAIL cmd` → 能灌回来 |
| 8 | 吞吐实测 | 记录整包耗时，和本文 §3.7 的 5.7 s 估算对照 |
| 9 | 长稳 | 连续升级 20 次，暂存区不出现"写坏的 READY" |

## 7.1 实测结果（2026-11-23 16:15，ISO-TP 传输层已通过）

链路：PC → TCP 5000 → F407 网关 → CAN 500 kbps → F103。
判据是"PC 独立算的 CRC16/KERMIT 与 F103 串口打出来的 CRC 完全一致"。

| 用例 | 帧数 | PC 算的 CRC | F103 打出的 | 结论 |
|---|---|---|---|---|
| 256 字节（多帧满窗） | 37 | `0x0201` | `n=256 crc=0201` | 通过（256/256 字节一字不差） |
| 7 字节（单帧路径） | 1 | `0x5A4B` | `n=7 crc=5A4B` | 通过 |
| 8 字节（末帧不满 7） | 2 | `0x8B2A` | `n=8 crc=8B2A` | 通过 |
| 300 字节（超 288 缓冲） | 43 | 无 | 无输出 | 通过（回 `OVFLW` 拒收，不撑爆缓冲） |
| 漏发第 5 帧（序号跳号） | 36 | 无 | 无输出 | 通过（整包作废，不拼出错包） |

F407 侧全程 `drop=0 bad=0 ack=0`。

**踩到并修掉的两个坑**：

1. F407 只有 3 个发送邮箱，一次 TCP 段塞 4 条 `CAN` 命令时第 4 条撞上"邮箱没排空"被丢掉
   （`drop=1`）。改成失败后 `HAL_Delay(1)` 重试最多 3 次。
2. PC 脚本自己写错：同步时只 `read_line()` 没发 `Q`，等一行永远不会来的数据，表现为 3 秒超时。
   改成 `cmd("Q")`（发 + 读）。

## 7.2 UDS 服务层实测（2026-11-23 16:25，第一步：骨架 + 10/3E/11）

`uds.c` 只做报文进、报文出，不碰 Flash。`TEST_ISO_TP_DUMP=1` 时每条收发都打到串口。

| 请求 | 期望响应 | 实测 | 结论 |
|---|---|---|---|
| `3E 00` | `7E 00` | `7E 00` | 通过（修了一个字节，见下） |
| `3E 80` | 无响应（抑制位） | 只有 RX，无 TX | 通过 |
| `10 03` | `50 03 00 32 13 88` | 一致 | 通过（P2=50 ms / P2*=5000 ms） |
| `11 01`（扩展会话） | `7F 11 7F` | 一致 | 通过（只在编程会话允许复位） |
| `10 09` | `7F 10 12` | 一致 | 通过（子功能不支持） |
| `10`（长度不足） | `7F 10 13` | 一致 | 通过 |
| `22 F1 90` | `7F 22 11` | 一致 | 通过（未实现的服务） |
| `10 02` | `50 02 00 32 13 88` | 一致 | 通过 |
| `11 01`（编程会话） | `51 01` 然后复位 | `51 01` + `=== boot ===` | 通过 |

**S3 超时的间接验证**：切到编程会话 → 等 6 秒 → 发 `11 01`。如果 S3 定时器生效，
设备已经退回默认会话，复位就会被拒（`7F 11 7F`）。实测正是 `7F 11 7F`。

**抓到的 bug（我写的）**：`3E 00` 一开始回的是 `7E` 而不是 `7E 00`。
`Uds_Positive(sid, data, n)` 的 `n` 是"子功能之后的字节数"，我传了 0，于是只回了 1 个字节。
ISO 14229 要求肯定响应原样回子功能，严格的 Tester 会按长度不符判失败。
修法：把子功能当成第一个数据字节传进去。

## 7.3 UDS 安全访问 0x27 实测（2026-11-23 16:40）

`0x27` 是挑战-响应：设备回种子，Tester 算密钥送回去。**所以这一层必须有回程通道**，
于是给 F407 的命令通道加了 `CAP <id>`（布置抓帧）和 `CAPQ`（读回抓帧槽）两个命令。

主流程（`sec_test.py`）：

| 步骤 | 请求 | 期望 | 实测 |
|---|---|---|---|
| 退回默认会话（清状态） | `10 01` | `50 01 00 32 13 88` | 一致 |
| 切编程会话 | `10 02` | `50 02 00 32 13 88` | 一致 |
| 未解锁就复位 | `11 01` | `7F 11 33` | 一致 |
| 没求种子就送密钥 | `27 02 00 00 00 00` | `7F 27 24` | 一致 |
| 求种子 | `27 01` | `67 01 <4字节>` | 种子 `D74429EF` |
| 送正确密钥 | `27 02 F5 1E 0F 06` | `67 02` | 一致 |
| 已解锁再求种子 | `27 01` | `67 01 00 00 00 00` | 一致（标准里"我已经开了"的信号） |
| 解锁后复位 | `11 01` | `51 01` + 重启 | 一致 |

密钥算法在 C 和 Python 里各写一遍，`D74429EF → F51E0F06` 两边一致，
说明"独立实现算出同一个值"这条判据成立。

三次错误锁定：

| 动作 | 响应 |
|---|---|
| 第 1、2 次送错密钥 | `7F 27 35`（invalidKey） |
| 第 3 次送错密钥 | `7F 27 36`（exceedNumberOfAttempts，同时上锁 10 分钟） |
| 锁定后求种子 | `7F 27 36` |
| 锁定后送密钥 | `7F 27 36` |

三次种子分别是 `20C2ACD8` / `BFBE975A` / `C3B8AD3B`，互不相同，说明熵源有效。

**抓到的固件 bug（真 bug，不是测试问题）**：切会话没有清安全状态。
表现是脚本重复跑时，"未求种子先送密钥"的响应从 `7F 27 24` 变成了 `7F 27 35` ——
因为上一轮留下的种子还在。ISO 14229 要求退回默认会话必须清除解锁状态。
修法：任何会话切换清掉待用种子，退回默认会话时连"已解锁"和失败计数一起清。

**抓到的测试脚本 bug（我自己的）**：`27 01` 的响应是 6 字节（`67 01` + 4 字节种子），
脚本里按 5 字节判断，导致明明收到种子却报失败。

## 7.4 UDS 0x28 通信控制实测（2026-11-23 16:50）

这一组的判据和前几组不同：不看响应对不对，看**总线行为变没变**。
唯一客观指标是 F407 的接收帧计数 `rf`（`GET /data`）。

| 步骤 | 期望 | 实测 |
|---|---|---|
| 默认状态下 2 秒内 `rf` 增长 | > 0 | 20 |
| 默认会话关总线 `28 03 01` | `7F 28 7F` | 一致 |
| 切扩展会话 `10 03` | `50 03 00 32 13 88` | 一致 |
| 通信类型不支持 `28 03 02` | `7F 28 31` | 一致 |
| 长度不足 `28 03` | `7F 28 13` | 一致 |
| 关总线 `28 03 01` | `68 03` | 一致 |
| **关之后 2 秒内 `rf` 增长** | **0** | **0** |
| 开回总线 `28 00 01` | `68 00` | 一致 |
| **开回之后 2 秒内 `rf` 增长** | **> 0** | **20** |
| **关掉后不再发 3E，等 7 秒** | `rf` 自动恢复增长 | 20（S3 超时安全网生效） |

最后一行是安全网：Tester 把总线关掉后如果自己挂了（或线断了），
5 秒的 S3 定时器必须把设备恢复到默认状态并重新发送。
不验这一条，一次异常升级就能让设备"永远静默"，现场只能拔电。

**0x85 故障记录开关**同时实现：`Event_LogFail()` 入口加门，刷写期间不写假故障。
理由：升级时设备不采集、SD 也停了，故障统计会把"数据流断了"记成故障，
刷一次固件就往卡里写一堆假记录，事后数据全被污染。

## 7.5 UDS 0x31 例程控制实测（2026-11-23 22:30）

这是第一组**真的会擦外部 Flash**的用例，所以多了两个前几组没有的判据：
擦除期间要多次收到 `0x78`；擦完之后"校验"必须报"没有暂存镜像"。

| 用例 | 期望 | 实测 |
|---|---|---|
| 未解锁擦除 | `7F 31 33` | 一致 |
| 解锁后 `31 01 FF00` 擦暂存区 | `71 01 FF 00 00` | 一致，**耗时 1.2 s** |
| 擦除期间抓到的帧数 | > 1（27 扇区擦不完 5 秒内） | **7 帧** |
| 擦完 `31 01 0202` 校验 | `71 01 02 02 01`（无镜像） | 一致 |
| 不存在的例程 `31 01 1234` | `7F 31 31` | 一致 |
| 不支持的子功能 `31 02 FF00` | `7F 31 12` | 一致 |
| 长度不足 `31 01 FF` | `7F 31 13` | 一致 |

**7 帧的构成**（能对上说明分步逻辑没写错）：1 次开场 `0x78` + 5 次"每擦完 5 个扇区
再报一次忙" + 1 次最终肯定响应。27 扇区 ÷ 5 = 6 批，前 5 批各补一次 `0x78`。

擦除 1.2 s ≈ 27 × 44 ms，和 W25Q64 手册的扇区擦除典型值 45 ms 吻合。

### 分步擦除为什么必须这么写

`P2* = 5000 ms` 是 Tester 收到 `0x78` 之后愿意等的时间。
27 个扇区最坏 27 × 400 ms = **10.8 秒**，一次擦完必然超时。
所以拆成"每批 5 个扇区 → 补一句 `0x78`"，任何时刻 Tester 等的都不超过 2.4 秒。

### 抓到的 bug：W25Q64 驱动的返回值约定看反了

第一版 `ota_stage.c` 里所有判断都写成"返回 0 才算成功"，
而实际约定是 **1 = 成功、0 = 失败**（`W25Q64.h` 每一条注释都写了）。

现象：擦除只用了 0.1 秒，状态码回 `03`（W25 不在位）——
因为第一次 `EraseSector` 返回 1（成功），被当成失败直接跳出了。

**更坑的是同一个驱动里两套约定**：

| 函数 | 约定 |
|---|---|
| `ReadData` / `WriteData` / `EraseSector` / `EraseBlock64K` / `WaitReady` | **1 = 成功** |
| `W25Q64_SelfTest` | **0 = 全过**（非 0 = 第几步坏的） |

修完之后每一处判断都写成 `== 0 才算失败`，并把这个坑记进了 `ota_stage.c` 的抬头。

### 已知代价

擦除期间 PROC 被阻塞约 1.2 秒（最坏 10.8 秒），采集任务会因为队列写满而丢这段数据。
正式产品应当把擦除挪到独立低优先级任务，并在升级前显式暂停采集。
本版先接受这个代价，因为升级本身就是一次计划内的停机。

> ▸ **CAN-OTA 双通道升级**：在 F103 上实现 ISO-TP + UDS 子集，镜像经 F407 网关转发后落 W25Q64
> 暂存区，复位由 Boot 校验搬运；保留串口停等线刷作为救砖通道。整包升级 ≈6 s（串口 20 s）。
