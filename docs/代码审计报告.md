## 0. 先给结论

任务书里多处「我的说法」经核对**成立**（`active` 只在任务上下文写、`s_cmd` 的字段不交叉、`Event_LogFail` 不在临界区里被调且不阻塞、POST 的 `memcmp` 边界够、AUTH 的前缀与长度处理正确、上位机 `_reader` 不碰 `curves`）；但**成立的这几条恰好都不是最危险的地方**。

## 一、P0 —— 会导致数据错误 / 死机 / 安全漏洞

### [P0] 一条对端 FC 帧就能让网关主循环停摆数秒，`STmin` 是外部可控的阻塞时限

- **位置**：`can_gw.c:268-323`（`CanGw_WaitFc`）、`can_gw.c:473-476`（`HAL_Delay(stmin)`）、`net_tcp.c:434`（调用点）、`main.c:971-1008`（主循环）
- **现象/风险**：`CanGw_FwdIsoTp` 由 `Fwd_Exec` → `Net_TcpPoll` → `main()` 主循环调用，是**裸主循环上下文**。`CanGw_WaitFc` 用 `HAL_Delay(1)` 忙等最长 `CAN_GW_ISOTP_FC_TIMEOUT=100 ms`；每发完一帧 CF 还会 `HAL_Delay(s_isotp_fwd.stmin)`，而 `stmin` 直接取自对端 0x3E0 流控帧的 `data[2]`，`0x00..0x7F` 被原样当成毫秒（最大 127 ms）。一条 37 帧的报文，最坏 `37 × 127 ms ≈ 4.7 s` 主循环不返回，**LVGL 刷新、Modbus TCP、HTTP、5000 命令通道、链路检测全部停摆**。对端只要正常发一个 `STmin=0x7F` 的 CTS 就能触发，不需要任何畸形报文。
- **依据**：`main.c:1000-1002` 三个 Poll 与 `main.c:1008` 的 `HAL_Delay(1)` 在同一 `while(1)` 内；`can_gw.c:290` `s_isotp_fwd.stmin = (st <= 127u) ? st : 1u;`；`can_gw.c:475` `HAL_Delay(s_isotp_fwd.stmin);`。`F407-稳定性观察` 里 `wmax=20` 只说明历史 FC 都很快，不代表上限安全。
- **建议**：把 `stmin` 钳到一个演示可接受的上限（如 5 ms），或把 ISO-TP 转发搬出主循环（专用任务 / 状态机 + 时间戳非阻塞等待）；`CanGw_WaitFc` 的超时不要靠 `HAL_Delay` 轮询。
- **置信度**：确定（代码路径可静态完整追踪）

### [P0] OVFLW 后的 `dropping` 会静默吞掉所有后续 CF，且超时路径走了完全相反的行为

- **位置**：`can_gw.c:395-433`（CF 分支）、`can_gw.c:342-346`（SF 复位）、`can_gw.c:372-380`（FF 复位）
- **现象/风险**：
  1. `WaitFc` 收到 OVFLW 时把 `active=0`，调用方置 `dropping=1`；此后每个 CF 走 `active==0 && dropping!=0` → **直接 `return HAL_OK` 丢帧**。`net_tcp.c:436` 见 HAL_OK 就 `g_fwd_can_ok++`，`Q` 里的 `ok` 上涨、`drop` 为 0 —— **指标显示"全部转发成功"，实际数据被吞**。
  2. `dropping` 只在收到 **SF(0x00) 或 FF(0x10)** 时清零。若重传/续传不发新 FF（只补 CF），或新报文的 FF 恰因邮箱满被丢弃，状态会一直卡在丢弃态。
  3. **超时路径不一致**：`fst == HAL_TIMEOUT` 时既不置 `dropping` 也不清 `active`，而是 `bs_left=0xFF; stmin=0; need_fc=0`（`can_gw.c:426-432`），之后**不等任何 FC 继续灌 CF**。OVFLW 是"全丢"，超时是"全发且无流控"，同一类失败两种相反行为。长稳记录里 `to` 一夜涨 1 次，正是走了后者。
  4. `s_isotp_fwd.fc_ready` 只在 FF 时清零、在 `WaitFc` 消费时清零，**没有报文归属校验**：对端多发一个 FC（或上一个报文残留的 FC）会被下一个报文当成首个 CTS 立即消费，跳过等待。
- **依据**：`can_gw.c:400-403` `return HAL_OK;`（丢弃却报成功）；`can_gw.c:421-423`；`can_gw.c:426-432`；`can_gw.c:380` `fc_ready = 0u;`。
- **建议**：丢弃帧时返回可区分的状态并计入 `g_fwd_can_drop`；`dropping` 增加超时/计数器兜底复位；给 FC 加报文序号或至少按 FF 计数做归属匹配；统一 OVFLW 与 TIMEOUT 的处理策略。
- **置信度**：确定

### [P0] 布局版本检查只计数、不拒绝解析，注释承诺的保护根本没实现

- **位置**：`can_gw.c:643-650`（检查）、`can_gw.c:681-708`（0x103/0x104 解析）、`freertos_demo.c:1065-1069`（承诺）、`net_tcp.c:456-461`（`AQ`）
- **现象/风险**：F103 注释写「网关收到不匹配的版本会拒绝解析 —— 否则两端不同步时数据安静错位」，但 F407 实际只做 `layout_ok = (proto_ver == GW_LAYOUT_VER)` 和 `layout_bad++`，**之后 0x103/0x104 的解析分支里没有任何 `layout_ok` 判断**。版本不匹配时，旧布局的字节仍按新布局解出 ax/ay/az/vbat、gx/gy/gz/light，照常写入 Modbus 寄存器、`/data` 和屏幕。`AQ lv=2 ok=1 bad=60` 里的 `bad=60` 说明确实收到过 60 帧不匹配帧，**这 60 帧的数据是被照常解析的**。
- **依据**：`can_gw.c:646-650` 与 `can_gw.c:681`/`696` 两个 `else if` 之间无 gates；`App_SyncFromCan`（`main.c:798-821`）也不检查 `layout_ok`。
- **建议**：在 `0x103/0x104` 解析入口加 `if (s_data.layout_ok == 0u) return;`，或让 `App_SyncFromCan` 在版本不匹配时冻结扩展量并置 `valid=0`；同时把"拒绝"写进回归用例（发一帧 `s[3]=1`，检查 `/data` 的 `ax/gx` 不更新）。
- **置信度**：确定

### [P0] 今天新增 8 个 JSON 字段后，192 字节缓冲会静默截断，`/data` 返回残缺 JSON

- **位置**：`web_srv.c:56`（`WEB_JSON_BUF 192u`）、`web_srv.c:245-299`（`Web_BuildJson`）、`web_srv.c:130-137`（`CatCh`）、`recorder_gui.pyw:577-578`
- **现象/风险**：任务书写「JSON 补 4 个量」，**代码实际补了 8 个键**（`vb/lx/ax/ay/az/gx/gy/gz`）。按当前典型值核算输出 **164 字节**，只剩 27 字节余量。下面两种情况都会越界：
  - 把参数区 4~9 写成 5 位数（`/set` 允许 0~65535），且 `rf`/`mq` 等计数随时间变长 → **193 字节**，`CatCh` 停在第 191 字符，正好丢掉结尾 `"}`；
  - 满量程 → **236 字节**，`pr` 段和结尾全丢。

  `CatCh` 是**静默丢弃**，没有任何计数或日志。结果是 `/data` 返回 `Content-Length` 与实际一致但 JSON 语法不完整，浏览器 `r.json()` 和上位机 `json.loads()` 抛异常，**网页与网络数据源的所有数值同时停止刷新**，而设备侧看不出任何异常。
- **依据**：逐字段复算（典型 164 B / 参数区 5 位数 + 运行一天 193 B / 满量程 236 B）；`CatCh` 上限为 `s_out_max-1 = 191` 字符。
- **建议**：`WEB_JSON_BUF` 提到 ≥ 256（或直接复用 `s_tx` 分段发）；更好的做法是让 `Web_BuildJson` 返回"是否截断"并在截断时回 500 + 计数，同时加一条「写满 6 个 65535 再读 `/data`」的回归用例。
- **置信度**：确定（算术可复现）

### [P0] `s_ready_mask` 读改写会丢位，且双缓冲不保证「先到先处理」

- **位置**：`iso_tp.c:91`（声明）、`iso_tp.c:221/325`（中断 `|=`）、`iso_tp.c:474`（任务 `&=`）、`iso_tp.c:437-444`（`IsoTp_Take`）
- **现象/风险**：
  1. **丢位**：`s_ready_mask` 是普通 `uint8_t`（**连 `volatile` 都没有**）。任务侧 `IsoTp_Release` 的 `&=` 编译成 LDRB/BIC/STRB；若中断在 LDRB 与 STRB 之间把另一槽置位，任务的 STRB 会把这个新位覆盖掉 → 那一包永远不会被 `Take`，而 `IsoTp_PickSlot` 又认为该槽空闲，**后续新包直接覆盖它的数据**。这正是任务书 3.4① 问的竞态，答案是**会丢位，确实存在**。
  2. **不保序**：`IsoTp_Take` 注释写「固定先给槽 0 再给槽 1：先到的那包必须先进处理」，但 `s_ready_mask` **只记录哪些槽有包，没有记录到达顺序**。可达反例：包 A 在槽 0 被 Take→Release 后，包 B 进槽 1（`mask=0x02`），此时包 C 到达，`PickSlot` 优先给空着的槽 0，`mask=0x03`，下一次 `Take` 返回**槽 0 的 C**（后到），B 反而被压后。对按块顺序写 Flash 的 OTA，这是块序错乱。312 块测试 0 失败是因为每块都要等响应、实际没形成双槽积压，属于「主路径没走到」，不是「不会错」。
- **依据**：`iso_tp.c:474` `s_ready_mask = (uint8_t)(s_ready_mask & (uint8_t)~(uint8_t)(1u << s_take_slot));`；`iso_tp.c:443` `slot = ((s_ready_mask & 0x01u) != 0u) ? 0u : 1u;`。
- **建议**：`s_ready_mask` 加 `volatile`；`Release` 的读改写用 `taskENTER_CRITICAL()/taskEXIT_CRITICAL()` 或 `LDREXB/STREXB`；用「每槽单调递增序号」或环形队列代替固定槽 0 优先，才能真正保证顺序。
- **置信度**：确定（竞态窗口与乱序路径均可静态构造）

## 二、P1 —— 影响可靠性 / 可维护性

### [P1] `POST /set` 不检查 Content-Length，header 与 body 分段到达时会误回 400

- **位置**：`web_srv.c:539-542`（`Web_Handle`）、`web_srv.c:465-481`（找 `\r\n\r\n` / `body_len==0`）、`web_srv.c:649-668`（recv 后立即 `Web_Handle`）
- **现象/风险**：`Web_ReqComplete()` 只找请求头结束的 `\r\n\r\n`，找到就立刻处理 POST。但 `Web_ChanPoll` 是**每次 `recv` 后立刻调 `Web_Handle`**，没有等 `Content-Length` 指定的 body 收齐。若 TCP 把 header 和 body 拆成两个段（网络稍慢、包稍大、代理介入都会），第一次处理时 `body_len=0` → 回 `400 no body` → `drain` 关连接，合法的写参数请求被丢掉。
- **依据**：`web_srv.c:465-476` 只按已收字节算 body；`web_srv.c:476-481` 直接 400；`web_srv.c:667` 无等待。
- **建议**：解析 `Content-Length`，`rx_len < header_end + 4 + content_length` 时返回继续收；或至少在 body 为空时再等一个轮询周期。用 `curl -d` 带 500+ 字节 body、人为分段发（或 `TCP_NODELAY` 关掉）能复现。
- **置信度**：较可能（协议路径确定，触发取决于实际分段；任务书的 `Invoke-WebRequest` 小请求一次发完，测不出）

### [P1] 0x103 / 0x104 交替发送，加速度与角速度永远差 100 ms，姿态融合用的不是同一时刻数据

- **位置**：`freertos_demo.c:1089`/`1116`（`rec.seq & 1` 交替）、`can_gw.c:681-708`、`web_srv.c:270-285`、`recorder_gui.pyw:692-708`
- **现象/风险**：今天把 ax/ay/az 挪进 0x103、gx/gy/gz 挪进 0x104 解决了「三轴同帧」，但**两帧仍是按 seq 奇偶交替、各 5 Hz**。一次 `/data` 拿到的 `ax/ay/az` 来自偶数 seq，`gx/gy/gz` 来自相邻的奇数 seq，**相差 100 ms**。`_update_attitude` 的互补滤波同时用 `row["ax/ay/az"]` 和 `row["gx/gy"]`，输入本身不同时刻，注释里「实测偏 11 度」的问题只是从"三轴之间"搬到了"加速度与角速度之间"。
- **依据**：`freertos_demo.c:1089` `if ((rec.seq & 1u) == 0u)` / `1116` `!= 0u`；`recorder_gui.pyw:695-708` 同一个 `row` 里同时取两组。
- **建议**：要么四帧同拍发（需解决 3 邮箱限制，可让 0x101/0x102 错拍），要么在帧里带 `seq` / 采集时刻，由网关按 seq 对齐后再合成一个快照；`/data` 至少应暴露两组数据各自的 seq，让消费端能判断是否同拍。
- **置信度**：确定

### [P1] 网络数据源没填 `tick` / `seq`，姿态积分 dt 恒用 0.1 s，运行时长与 CSV 行数恒为 0

- **位置**：`recorder_gui.pyw:581-594`（构造 row）、`607-629`（`_feed_row`）、`697-702`（dt）、`628`（`up_s`）、`619`（CSV 行数）
- **现象/风险**：`_net_poll` 构造的 row 只有 11 个物理量，`_feed_row` 用 `row.setdefault(k, 0)` 把 `tick`/`seq` 补成 0。后果：`_update_attitude` 里 `d = (row["tick"] - att_last_tick)/1000` 恒为 0，永远落不进 `[0.02, 1.0]`，**dt 恒用默认 0.1**，而实际轮询是 150 ms → 陀螺积分偏 50%，姿态角系统性漂移；仪表盘 `up_s` 恒 `0s`；CSV 行数显示恒 0。
- **依据**：`recorder_gui.pyw:601-605` 轮询 150 ms；`697-701` 的 dt 分支。
- **建议**：网络模式下用本地单调时钟生成 `tick`（如 `time.monotonic()*1000`），`seq` 用自增计数；或在 `_update_attitude` 里按数据源分别取 dt。
- **置信度**：确定

### [P1] 0x103/0x104 布局改了代码，但至少 6 处注释/结构体分组仍是旧布局

- **位置**：`can_tx.h:42-43`、`can_gw.h:177-178` 与 `64-76`、`freertos_demo.c:1082` 与 `1112`、`modbus_tcp.h:8-10/31-35/50`
- **现象/风险**：任务书 3.3 的担心**命中了，且不止一处**。例如 `can_gw.h:177` 仍写 `0x103 /* 电池(2) + 光照(2) + ax(2) + ay(2) */`，`freertos_demo.c:1082` 标题仍是「电池 / 光照 / 加速度 XY」，`can_tx.h:43` 仍写 0x104 是「加速度 Z / 角速度 XYZ」。`CanGwData_t` 的字段分组注释把 `light` 归进 0x103 组、`az` 归进 0x104 组，与实际赋值完全相反。另有 `modbus_tcp.h:32-35` 写「16 -> 20」而宏实际是 `MODBUS_REG_COUNT 24u`，`:31` 写「合法地址 0~15」，`:8-10` 的功能码清单里没有 0x04。
- **依据**：与 `freertos_demo.c:1097-1104`/`1121-1128` 及 `can_gw.c:685-692`/`699-706` 逐字节比对 —— **两端实际字节序是一致的，功能正确，错的全是注释**。
- **建议**：把这些注释一次性同步；`MODBUS_REG_COUNT` 用编译期断言或直接由枚举生成，避免"改宏忘改注释"。
- **置信度**：确定

### [P1] `CQ` 的 ACK 字段会跨中断撕裂，比 `s_alarm` 更值得管

- **位置**：`can_gw.c:505/531-534/660-666`、`net_tcp.c:466-476`
- **现象/风险**：任务书 3.1② 问 `s_alarm` 撕裂有没有实际危害 —— **答案：基本没有**。`CanGw_GetAlarm()` 的唯一消费点是 `AQ`（`net_tcp.c:454`），纯文本显示，最坏是显示「新 ch + 旧 count」，没有任何控制逻辑依赖它。但**同类问题在 `s_cmd` 上更实际**：`CQ` 是命令闭环的唯一判据，`ack_cnt`(32 位原子) 与 `ack_code/ack_result`（两个独立 8 位）之间无快照一致性；连续下发 `CMD 02` → `CMD 01` 时，完全可能读到 `ack_cnt` 已增、而 `res` 还是上一条的旧值，上位机会误判执行结果。此外 `CanGwCmd_t` / `CanGwAlarm_t` / `CanGwData_t` 的成员都**没有 volatile**，`CanGw_GetXxx()` 返回 `const` 指针，编译器可在一次 `snprintf` 内缓存字段。
- **建议**：`CQ` 读取时用临界区拷一份本地快照（或按 `ack_cnt` 前后两次读一致再采信其它字段）；结构体中被中断写的字段加 `volatile`。`s_alarm` 可维持现状但注释别再写「五个字段全部由中断写，任务只读」当作安全证明。
- **置信度**：确定（撕裂窗口），较可能（实际误判，取决于命令间隔）

### [P1] `CAN_CmdTake` 的「先读码再清标志」仍有丢命令窗口

- **位置**：`can_tx.c:196-228`（F103 侧，任务书 3.1② 只问了 F407 的 `s_cmd`）
- **现象/风险**：注释声称先读后清没有窗口，实际上**清标志这一步本身会覆盖中断置的 1**：中断在 `c = s_cmd_code` 之后、`s_cmd_pending = 0u` 之前写入新码并置 pending=1，随后任务把 pending 清 0，新命令永久丢失。单槽 + 20 ms 轮询下，两条命令间隔小于一拍就会触发。
- **建议**：`CAN_CmdTake` 内用 `__disable_irq()/enable_irq()` 或 `taskENTER_CRITICAL` 包住「读码 + 清标志」两步（此处是裸中断，不是 FreeRTOS 中断，临界区可行）。
- **置信度**：确定（窗口存在），较可能（实际发生）

### [P1] 39/39 回归测的是「打印了几个 [PASS]」，不是「流控是否正确」；OVFLW 与 `to` 都没被覆盖

- **位置**：`run_all.py:100-120`（`run_script`）、`run_all.py:149-198`（`suite_isotp`）、`isotp_test.py:201-221`
- **现象/风险**：

### [P1] F103 的 RAM 余量算错了，栈核算也用错了指标

- **位置**：任务书 §3.2；依据 `_build_p0_F103.log`、`Listings/Project.map`、`Start/startup_stm32f10x_md.s:33-48`、`Project.uvprojx`
- **现象/风险**：

  - 「给栈和堆」这个说法也不成立：map 第 5353 行显示 `STACK 0x20004348 size 0x400 (1024 B)` **已经含在 ZI 里**（`__initial_sp = 0x20004748 = 18248`），`HEAP (512 bytes)` 被链接器 `Removing` 掉了（用的是 `heap_4.o` 的静态 `ucHeap 64 B`）。剩下 2232 B 是纯空闲，不需要再从中分栈。

- **建议**：修正任务书数字；在 `task_KEY` 里用 `uxTaskGetStackHighWaterMark` 打一次实测值；把 `Serial_Printf` 从 `task_KEY` 挪走或关掉 `TEST_ISO_TP_DUMP`。

## 四、对任务书 3.1① 四个子问题的逐条回答

### `s_isotp_fwd.active` 真的只在任务上下文写吗？—— **是，这条说法成立**

中断路径 `HAL_CAN_RxFifo0MsgPendingCallback`（`can_gw.c:548-709`）只写 `fc_fs/fc_bs/fc_stmin/fc_ready`（591-594）、`s_data.*`、`s_cmd.ack_*`（662-665）、`s_alarm.*`（672-677），**没有一处写 `active/sent/bs_left`**。`CanGw_WaitFc` 里的 `active = 0u`（`can_gw.c:312`）也仍在任务上下文（调用链见 P0 第一条）。所以「两组不交叉」这个前提对 `active` 成立。
**但前提成立不等于状态机安全**：`fc_*` 三个字节由中断依次写入、任务侧依次读取，中间没有整体快照；更麻烦的是 `fc_ready` 不带报文归属，陈旧 FC 会被下一个报文消费（已并入 P0 第二条）。

### `dropping` 什么时候恢复？—— 见 P0 第二条

只在收到 SF 或 FF 时清零；OVFLW 后若重传不带新 FF 就永久卡住，且丢弃帧返回 `HAL_OK` 让指标显示成功。

### 「`bs_left == 0xFF` 递减 42 次变 0xD5，永远到不了 0」—— **这个推演不成立，但有个反方向的真问题**

`can_gw.c:459` 的条件是 `if ((s_isotp_fwd.bs != 0u) && (s_isotp_fwd.bs_left != 0xFFu))`，**0xFF 被显式跳过，压根不会进入递减**，所以不存在"递减到 0xD5"的路径。用 0xFF 当"不限"哨兵、`BS=0` 映射成 0xFF（`can_gw.c:284-286`）本身是对的 —— ISO-TP 里 BS=0 就是"后续不再发 FC"。

真正的问题是**哨兵值和合法 FC 值撞了**：如果接收端回的 FC 里 `BS=0xFF`（合法，表示"再发 255 帧后重新等 FC"），`can_gw.c:284-286` 会 `bs = 0xFF; bs_left = fc_bs = 0xFF`，于是被当成"不限"哨兵，**发送方再也不等下一个 FC**。ISO-TP 单包最长 4095 字节 ≈ 586 个 CF，超过 255 帧是可能的；此时对端在等一个不会来的 FC，或反过来多发一个 FC 变成陈旧 FC。
- **建议**：把"不限"用一个 `bool need_fc` 或独立的 `bs_unlimited` 标志表示，不要复用 `bs_left` 的数据域；或把 `BS=0xFF` 单独钳到 254。
- **置信度**：确定（代码路径），较可能（实际触发，需要 >255 帧的报文）

### `STmin` 微秒段按 1 ms 处理，会不会导致对端超时？—— **不会，风险方向相反**

`0xF1..0xF9` 表示 100~900 µs，压成 1 ms 是**变慢而不是变快**；接收侧等 CF 的 N_Cr 超时通常是 1000 ms 量级，1 ms 远在其内，不会让对端超时，代价只是吞吐下降（37 帧约多 33 ms）。需要留意的是 `0xFA..0xFF` 属协议保留值，现在也被一律压成 1 ms，规范上应拒绝或按最保守值处理。
**真正的超时/阻塞风险来自 ms 段**：`0x00..0x7F` 原样进 `HAL_Delay()`（最大 127 ms/帧），见 P0 第一条 —— 这是"我们等太久把主循环拖死"，不是"对端等太久超时"。
- **置信度**：确定

## 五、对任务书「特别希望被质疑的两条验证」的正面回答

### 4.1 「REC 行数从 15 降到 0」能不能证明记录真的停了？—— **不能**

- `CMD 02` → `App_ExecCmd` 只置 `g_pause=1`（`freertos_demo.c:1392-1394`），**不碰 `g_print_quiet`**；所以你担心的"只是打印被关了"这个**具体机制不是当前实现路径**，`g_print_quiet` 只在 KEY1（`1459`）和 `1859` 被改。
- 但**验证方法本身不成立**：`g_pause=1` 让 ACQ 在 `freertos_demo.c:803-806` 直接 `continue`，跳过采样与入队；`task_SD` 是**独立从队列取数据写卡**的，ACQ 停了以后队列里已积压的记录仍会被写完 —— `freertos_demo.c:1248-1257` 的注释自己写着「暂停采集后最后几条会一直捂在手里……秒级落盘」，说明暂停后确实还有写卡动作。
- 更根本的是：`REC,` 行的打印受 `g_rec_echo` 独立控制（`freertos_demo.c:1232`），**它是一个可被完全无关的机制伪造的代理量**。用「串口 REC 行数」去证明「SD 卡没再写」，测的是"没产生新记录 + 回显开着"，不是"写卡停止"。哪天有人把回显关了、或把 `g_pause` 语义改成只停打印，这个用例照样 15→0 全绿。
- **改法**：断言 CSV 文件大小 / 行数在 N 秒内不再增长，或读 `task_SD` 的 `f_write` 计数；同时把 `g_rec_echo` 固定为 1 写进前置条件。

### 4.2 「az=1632 与串口 az<1631> 对得上」是不是同一时刻？—— **不是，而且问题比你想的更大**

- 首先这两个数**本身就差 1**（1632 vs 1631），按你自己给的判据，它恰好说明是相邻两拍的值，而不是同一拍。这条"对得上"只证明了**字节序和换算正确**，没证明时间对齐。
- 更关键：`0x103`（ax/ay/az/vbat）与 `0x104`（gx/gy/gz/light）按 `rec.seq` 奇偶**交替发送，各 5 Hz**（`freertos_demo.c:1089/1116`）。所以 `/data` 里 az 和 gx/gy/gz 永远来自相邻两个采样，**差 100 ms**。今天重排解决的是"三轴加速度同帧"，但姿态解算用的是 `acc + gyro` 融合（`recorder_gui.pyw:692-708`），两组输入仍不同时刻 —— 见 P1 第三条。
- **改法**：帧里带 `seq` 或采集 tick；`CAP 103` / `CAP 104` 各抓一帧后用 seq 配对，只有 seq 相同才算对齐；`/data` 暴露两组数据各自的 seq。

## 六、总评

### 今天这批改动里，最危险的 3 处

1. **主循环被对端 FC 帧远程拖死**（P0 第一条）—— `CanGw_WaitFc` 的 100 ms 忙等 + 无上限的 `STmin` 全跑在 `main()` 的 `while(1)` 里。这是唯一一处「一条正常 CAN 帧就能让整台设备所有服务停摆数秒」的问题，且完全外部可控。
2. **流控失败后静默吞帧、指标显示成功**（P0 第二条）—— `dropping` 分支 `return HAL_OK` 让 `Q` 的 `ok` 涨、`drop` 为 0，同时超时路径又反着走"无流控全发"。数据错了但所有计数都说没问题，是最难在现场被发现的一类缺陷。
3. **192 字节 JSON 缓冲被静默截断**（P0 第四条）—— 今天一口气加了 8 个键（文档按 4 个量估的余量），典型值只剩 27 字节余量，参数区写成 5 位数或计数再涨几位就破。截断无日志、无计数，表现为"网页和上位机突然全不刷新"。

（紧随其后的是**布局版本检查空转**和 **`s_ready_mask` 竞态/乱序**，二者分别对应"以为有保护"和"以为有顺序"，也都属于静默错误。）

### 有没有哪一处会在面试 / 演示时被问倒？

**有，最可能被问倒的是「布局版本」这一处。**

> 追问链大概是这样：你会讲"我在 0x102 里加了 `layout_ver=2`，两端布局不一致时网关会拒绝解析，避免数据安静错位" → 面试官问「代码里哪一行拒绝的？」→ 只有 `layout_bad++`，没有拒绝 → 再问「那你 `AQ` 里的 `bad=60` 是什么？那 60 帧的数据去哪了？」→ 答不上来。

这一处特别危险，因为**你自己给出的验证数据 `bad=60` 恰好是反证**：它证明曾经有不匹配帧进来，而系统照常解析了。建议演示前要么补上拒绝分支，要么把话术改成"只做了告警计数，拒绝解析是下一步"。

另外三个高概率追问：

- 「三轴同帧解决了姿态解算的不同步，那加速度和角速度呢？」→ 仍差 100 ms，且 `az=1632` / `az<1631>` 这组数据自己就露了馅。
