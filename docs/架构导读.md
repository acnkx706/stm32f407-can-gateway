## 0. 一句话说清它是干什么的

**一块 240×240 彩屏的 CAN 网关**：从 CAN 总线收 F103 记录仪的数据，同时对外提供三种取数方式（网页 / Modbus / TCP 命令通道），并用图形界面实时显示链路状态。

它不是"采集板"，是**中转和展示**用的。数据源头是 F103 工业记录仪。

## 1. 硬件与资源

| 项 | 值 | 说明 |
|---|---|---|
| MCU | STM32F407ZGT6 | 168 MHz，1 MB Flash，128 KB SRAM |
| 开发板 | 鹿小班 LXB407ZG-P1 | |
| 时钟 | HSE 8 MHz → PLL M8 N336 P2 | APB1 = 42 MHz，APB2 = 84 MHz |
| 显示 | 240×240 ST7789，SPI3 | LVGL 8.3.9 |
| 输入 | EC11 编码器（PB6/PB7，TIM4 编码器模式） | 旋转切页，按下确认 |
| 网络 | W5500，SPI1，42 MHz | 硬 TCP/IP，不占 MCU |
| CAN | CAN1，PB8/PB9（AF9），500 kbps | 标准 11 位帧 |
| 网络参数 | IP `192.168.10.50/24`，MAC `02:00:00:00:00:01` | 电脑 `192.168.10.100/24` 网线直连 |

**为什么 CAN 用 PB8/PB9 而不是 PA11/PA12**：PA11/PA12 是 USB 的 D-/D+，板上接到 USB 座，复用成 CAN 有干扰风险。

**为什么 PB8/PB9 只能跑 CAN 或 I2C 二选一**：同一个引脚，`CAN_ENABLE` 宏决定走哪条。当前 `CAN_ENABLE != 0`，I2C 从机代码不编译。

## 4. 主循环（`main()` 末尾）

```c
while (1)
{
    /* ---- 5 ms 一拍 ---- */
    if ((HAL_GetTick() - last_tick) >= 5u)
    {
        lv_timer_handler();          // LVGL 内部定时器（动画、重绘）
        Ui_Update(link_up);          // 刷新界面数值
        CanGw_Poll();                // 维护"链路有效"标志（500 ms 无帧就置 0）
        App_SyncFromCan();           // CAN 解出的值 → g_reg
        Modbus_PushData(link_up);    // g_reg → Modbus 寄存器
    }

    /* ---- 三个网络服务，各自带内部限速 ---- */
    Net_TcpPoll();                   // 2 ms 一次
    Modbus_TcpPoll();
    Web_SrvPoll();                   // 1 ms 一次

    HAL_Delay(1u);                   // ★ 关键，见下

    /* ---- 1 s ---- */
    if ((HAL_GetTick() - last_link) >= 1000u)  { 读 PHY 链路，变化才打印 }
    if ((HAL_GetTick() - last_stat) >= 1000u)  { 打印 [CAN] 统计行 }
}
```

**`HAL_Delay(1u)` 这一行不是随手加的**：早期主循环无间隔地敲 W5500 寄存器，SPI 时钟 21 MHz 时约每秒 5.6 万次事务，把芯片内部的命令仲裁器饿死，`Sn_CR` 写入变得时灵时不灵。加 1 ms 间隔后轮询率降了约 50 倍，TCP 延迟增加可忽略。

```

   PC ──TCP 5000──► │ net_tcp.c   文本命令 → CAN 帧         │──┐
                    ├──────────────────────────────────────┤  │
   PC ──TCP 502───► │ modbus_tcp.c  16 个保持寄存器        │  │
                    ├──────────────────────────────────────┤  ├──► CAN 总线
   PC ──TCP 80────► │ web_srv.c   HTML 页面 + /data JSON   │  │
                    └──────────────────────────────────────┘  │
                                                              │
   F103 ──CAN──────► can_gw.c ──解码──► CanGwData_t ──────────┘
                                          │
                          App_SyncFromCan()│
                                          ▼
                                        g_reg  ──► Modbus / Web / 屏幕
```

**`g_reg` 是唯一的数据中转点**。屏幕、Modbus、网页三处全读它，只有 `App_SyncFromCan()` 一处往里写。换数据源（比如改成 I2C 或本地传感器）只改这一个函数。

## 6. 各模块详解

### 6.1 `can_gw.c` — CAN 收发 + ISO-TP 流控（658 行）

**接收链路**：`HAL_CAN_RxFifo0MsgPendingCallback`（中断）里完成全部解码，不做任何打印和阻塞。

| CAN ID | 方向 | 内容 | 处理 |
|---|---|---|---|
| `0x080` | F103 → 网关 | 告警：ch(1) + reason(1) + 累计次数(2) + 保留(4) | 存 `s_alarm`，`AQ` 读取 |
| `0x101` | F103 → 网关 | 遥测：温度×100、湿度×10、气压(Pa)，小端 | 解到 `s_data` |
| `0x102` | F103 → 网关 | 状态心跳：seq(2) + status(1) + proto_ver(1) + rtc(4) | 按 seq 连续性算丢帧 |
| `0x201` | **网关 → F103** | 命令：cmd(1) + p1(1) + p2(1) + 保留(5) | `CMD` 命令触发，`CanGw_SendCmd` |
| `0x301` | F103 → 网关 | 应答：回显 cmd(1) + result(1) | 存 `s_cmd`，`CQ` 读取 |
| `0x2E0` | PC → 网关 → F103 | ISO-TP 诊断请求（UDS） | 转发，带发送侧流控 |
| `0x3E0` | F103 → 网关 → PC | ISO-TP 诊断响应 / 流控帧 | 抓帧槽 + 供发送侧等 FC |
| 其它 | — | — | 只计数；抓帧槽命中时抄一份 |

**命令码**（`can_gw.h` 与 F103 的 `can_tx.h` 必须一致）：

| 码 | 含义 | F103 侧动作 |
|---|---|---|
| `0x01` | 开始记录 | `g_pause=0` 并清关机态 |
| `0x02` | 停止记录 | `g_pause=1` |
| `0x03` | 翻页 | `g_page_next=1` |
| `0x04` | 蜂鸣 | `Buzz_Request` |
| `0x10` | 立即上报状态 | 通知 PROC 打统计 |
| 其它 | — | 回 `result=1`（未知命令） |

**为什么这是"网关"而不是"转接头"**：没有 `0x201`/`0x301`，F407 就只能被动收数据，想控制 F103 得靠 PC 从 TCP 转发进来 —— 断网就失控。

**关键设计：抓帧槽 `g_can_cap_id`**
命令通道只能往总线发，读不到回程，UDS 的"挑战-响应"就做不了。所以加了 `CAP <id>` 布置一个抓帧槽、`CAPQ` 读回最后一帧。一个槽而不是队列：一次只等一条响应，够用且省 RAM。

**发送侧流控 `CanGw_FwdIsoTp()`（2026-11-23 加）**

转发 `0x2E0` 时按 ISO 15765-2 发送侧规矩走：

- **SF**（高 4 位 0）：直接发，无流控
- **FF**（高 4 位 1）：记下总长度，发完置 `need_fc`
- **CF**（高 4 位 2）：块配额用完就等 FC，等到才发

**为什么必须加**：F103 的 CAN 接收 FIFO 硬件深度只有 3 级。原来无脑推 8 帧，第 4 帧就溢出；丢一帧整包作废，剩下的连续帧全被对端判成孤儿帧（串口就是连着几个 `why=6`）。

**代价**：一条多帧报文会让主循环阻塞到拿到 FC，最长 `CAN_GW_ISOTP_FC_TIMEOUT`（100 ms）。等超时降级为继续发，不卡死整包。

**实测**：311 次等 FC 共花 380 ms，最长一次 2 ms。

### 6.2 `net_tcp.c` — 命令通道（573 行，socket 0，端口 5000）

一行一条命令，`\n` 结尾。

| 命令 | 回复 | 需要认证 | 用途 |
|---|---|---|---|
| `PING` | `PONG` | 否 | 冒烟测试 |
| `Q` | `Q rf=.. tx=.. ok=.. drop=.. bad=.. ack=.. ff=.. cf=.. fc=.. to=.. wms=.. wmax=..` | 否 | 全部计数 |
| `AUTH <token>` | `AUTH OK` / `AUTH FAIL` | 否 | 解锁写操作，口令见 `NET_TCP_TOKEN` |
| `CAN <3位hex> <连续hex>` | 无（成功时） | **是** | 往总线发一帧 |
| `CMD <2位hex>` | 无（成功时） | **是** | 往 `0x201` 下发命令给 F103 |
| `CQ` | `CQ cmd=.. ack=.. res=.. n=.. m=..` | 否 | 命令下发状态（n=发出, m=收到 ACK） |
| `AQ` | `AQ ch=.. rsn=.. cnt=.. total=..` | 否 | 故障告警状态 |
| `CAP <3位hex>` | `CAP xxx` | 否 | 布置抓帧槽 |
| `CAPQ` | `RX <id> <hex..>` 或 `NONE` | 否 | 读回抓到的帧 |
| `CAPN` | `N <次数>` | 否 | 抓到了几帧 |

**认证策略（2026-11-24 加）**：只保护"会动到现场设备"的写操作（`CAN`、`CMD`），读操作全部放行，方便只做监控的客户端。

**为什么要做**：原来 5000 端口完全裸奔，同一网段任何人 `telnet` 进来就能往 CAN 总线发任意帧。

**局限**：口令硬编码在固件里（`"can-gw-2026"`），属于演示级防护。量产应改成每台设备唯一的密钥。

**两个已知陷阱**

**两个坑（2026-11-24 踩过）**：

1. **hex 必须连写，不能带空格**。解析器遇到空格就 `break`，`CAN 2E0 02 3E 00` 只会发出 1 个字节。
2. **ISO-TP 要求 DLC 等于 8**，短帧一律丢。即使只有 2 个有效字节也要补满 8 个。

### 6.3 `modbus_tcp.c` — Modbus TCP 从站（783 行，socket 1，端口 502）

- 16 个保持寄存器（`MODBUS_REG_COUNT`）
- 8 个线圈（`MODBUS_COIL_COUNT`）
- **功能码：`01` 读线圈、`03` 读保持寄存器、`04` 读输入寄存器（2026-11-24 补）、`05` 写单线圈、`06` 写单寄存器、`10` 写多寄存器**
- 写寄存器范围限制在 `4..9`

**`03` 和 `04` 读的是同一张表**：Modbus 语义上 04 读只读区、03 读可读写区，但本从站两类数据本来就是同一张表，硬拆成两套只会让人对不上号。响应里的功能码按请求回显，所以 `Mb_BuildRead` 多了一个 `fc` 参数。

**寄存器映射**（从实测响应反推）：

| 寄存器 | 内容 | 编码 |
|---|---|---|
| 0 | 温度 | ×100 |
| 1 | 湿度 | ×10 |
| 2 | 链路状态 | 0/1 |
| 3 | 保留 | |
| 12 | 帧计数 | |
| 15 | 版本 | |

### 6.4 `web_srv.c` — HTTP 服务器（587 行，socket 2~7，端口 80）

- 6 个并发连接（`WEB_SN_FIRST=2`，`WEB_SN_COUNT=6`）
- 接收缓冲 640 B，发送 2000 B，JSON 缓冲 192 B
- 页面存在 Flash 里，不占 RAM
- `/data` 返回 JSON：`{"t":19.62,"h":52.9,"p":1024.89,"rf":27812,"er":0,"mq":0,"me":0,"pr":"..."}`

### 6.5 `w5500_port.c` — W5500 移植层（1304 行）

SPI1 引脚：PA5=SCLK、PA6=MISO、PA7=MOSI、PA4=CS、PB10=RST。时钟 42 MHz（APB2/2），模式 0。

**SPI 速度是踩过坑的**：早期用 SPI2 在 PCLK1/2（21 MHz）时 `Sn_CR` 写入时灵时不灵，换成 SPI1 42 MHz 才稳定。

## 12. 一句话总结每层

| 层 | 一句话 |
|---|---|
| 硬件 | F407 + W5500 + ST7789 + CAN 收发器，网线直连电脑 |
| 驱动 | W5500 走 SPI1 42 MHz（SPI2 21 MHz 会丢命令）；屏走 SPI3 |
| 协议 | CAN 自定义应用层 + ISO-TP 传输 + UDS 子集（对 F103）；对外 Modbus/HTTP/文本 |
| 业务 | `g_reg` 单向汇聚，三处读取；UI 每 5 ms 刷，网络各带限速 |
| 界面 | LVGL 图形控件，三页 + 图标导航，无中文字体 |
