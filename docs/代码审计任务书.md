## 1. 项目背景（30 秒读完）

**两块板，一条 CAN 总线，500 kbps：**

```
F103 工业记录仪（采集）  ──CAN──►  F407 CAN 网关（中转 + 展示）
                                      ├─ Modbus TCP  502
                                      ├─ HTTP         80
                                      ├─ TCP 命令通道 5000
                                      └─ 240x240 LVGL 屏
```

**F103 只上报数据，F407 只中转和展示**，但 2026-11-24 给 F407 加了"主动下发命令"的能力（`0x201`/`0x301`）。

**数据来源：**
- F103 采集 11 个物理量，通过 4 条 CAN 帧发出去
- F407 收下来，映射到 24 个 Modbus 寄存器 / 一个 JSON 接口 / 屏幕三页
- PC 上位机（Python tkinter）从 JSON 或串口取数画 13 条曲线

## 3. 审计重点

### 3.1 【P0】我怀疑但没深究的地方

**① `can_gw.c` 的 ISO-TP 发送流控状态机（`CanGw_FwdIsoTp` / `CanGw_WaitFc`）**

**我的说法**：`s_isotp_fwd` 结构里 `active/sent/bs_left` 只由任务上下文写，`fc_*` 只由中断写，**两组不交叉所以不需要临界区**。

**请验证**：
- `s_isotp_fwd.active` 真的只在任务上下文被写吗？（中断路径里有没有？）
- `dropping` 标志的设计有没有漏：OVFLW 后丢弃后续 CF，什么时候恢复？
- `bs_left == 0xFF` 当"不限"的哨兵，递减 42 次后是 0xD5，永远到不了 0 —— 但如果一次传输超过 255 帧呢？
- `STmin` 微秒段按 1 ms 处理，会不会导致某些对端超时？

**② `can_gw.c` 里 `s_alarm` / `s_cmd` 的并发**

**我的说法**：`s_cmd` 的 `ack_*` 由中断写、`last_cmd/cmd_cnt` 由任务写，不交叉。

**请验证**：`s_alarm` 的五个字段**全部**由中断写，`CanGw_GetAlarm()` 返回指针给任务读 —— **32 位字段在 Cortex-M4 上是原子的，但 `ch/reason/count` 三个字段分开更新，任务侧可能读到"新的 ch 配旧的 count"**。这个撕裂有没有实际危害？

**③ `web_srv.c` 的 POST 解析**

**我的说法**：`Web_HandlePost` 里在 `c->rx` 整个缓冲区里搜 `"t=" NET_TCP_TOKEN`。

**请验证**：
- `memcmp(&c->rx[k], key, klen)` 的边界：`(k + klen) <= c->rx_len` 够不够？`rx` 是 640 字节固定缓冲，`rx_len` 会不会超过它？
- 搜整个缓冲区（含 body）而不是只搜请求行，**会不会有"body 里恰好包含这个字符串"就放行的情况？**（我认为这不算漏洞，但请你判断）
- `body_len == 0` 的判断在找 `\r\n\r\n` 失败时是否可靠？（`body` 初始化成 0，`body_len` 初始 0）

**④ `net_tcp.c` 的 AUTH 比较**

```c
        for (i = 0u; tok[i] != '\0'; i++)
        {
            if ((k >= n) || (s[k] != tok[i]))  { ok = 0u; break; }
            k++;
        }
        if ((ok != 0u) && (k != n)) { ok = 0u; }
```

**请验证**：
- 口令有前缀关系时会不会误判？（比如 `can-gw-2026` 和 `can-gw-2026x`）
- `tok[]` 是 `static const char`，`for` 循环用 `uint16_t i`，够不够？
- **时序攻击**：逐字节比较 + 提前 break，理论上可以用响应时间猜口令。演示级要不要管？

**⑤ `task_sd.c` 里 `Event_LogFail` 在 `sd_note_failure` 里调用**

**我的说法**：`sd_note_failure` 在 `task_SD` 里调，任务上下文，不会和 `Event_LogFail` 的临界区打架。

**请验证**：
- `sd_note_failure` 的四个调用点（2857/2860/2887/2948）**有没有一个在临界区里**？
- `Event_LogFail` 内部会调 `Uds_DtcDisabled()`，那个函数有没有可能阻塞？
- `Event_LogFail` 现在还会往 CAN 发帧（`CAN_TX_SendStd`），**如果 CAN 邮箱满会不会阻塞？**（我认为不阻塞，只是返回 0）

### 3.4 【P1】并发与竞态

**① `IsoTp` 双缓冲**

`s_ready_mask` / `s_fill` / `s_take_slot` 三个变量，收发两侧都碰：

- `s_ready_mask`：中断里 `IsoTp_PickSlot` 读、收齐时写；任务里 `IsoTp_Take` 读、`IsoTp_Release` 写
- `s_take_slot`：任务侧写，`Release` 读
- `s_fill`：中断侧写读

**请判断**：`s_ready_mask` 是 `uint8_t`，读改写（`|=` / `&=`）在 Cortex-M3 上**不是原子操作**。中断和任务同时改会不会丢位？

**② 上位机的 `curves` 列表**

串口线程和网络 `after()` 回调**都会往 `self.curves[k]` 里 append**。tkinter 的 `after` 在主线程，串口的 `_reader` 是独立线程 —— 但串口数据是通过 `queue` 传给主线程的（`self.lines_q`），所以**实际都在主线程**。

**请验证这个推理**：`_reader` 到底有没有直接碰 `curves`？
