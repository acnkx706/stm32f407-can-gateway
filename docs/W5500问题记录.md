## 一、一句话结论

**问题由两个因素叠加造成：**

1. **W5500 的 SPI 接在 PB13/PB14/PB15（SPI2）上，被同板的其他信号干扰**
2. **SPI 时钟太低（0.656 MHz），导致 `Sn_CR` 命令被芯片静默丢弃**

**解决方法：把这 5 根线整体改到 SPI1（PA5/PA6/PA7/PA4），并把 SCLK 提到 42 MHz。**

**结果：TCP 回显从 0/3 变成 12/12（3 次复位 × 4 组），1KB 数据完整收发。**

## 四、为什么"换引脚"比"提速度"更关键

**同为 21 MHz：**
- SPI2（PB13/PB14/PB15）：TCP 回显 **0/3**
- SPI1（PA5/PA6/PA7）：TCP 回显 **4/5**

**⇒ 引脚位置本身是主要因素。**

**最可能的原因：PB13/PB14/PB15 这组引脚在同一块板上被其他高速信号干扰：**

| 干扰源 | 引脚 | 与 W5500 信号的关系 |
|---|---|---|
| **LCD（SPI3）** | PB3(SCK)、PB5(MOSI) | 和 PB13~15 同属 GPIOB，物理相邻 |
| **EC11 编码器** | PB6、PB7 | 同属 GPIOB |
| **LCD 控制线** | PD11/PD12/PD13 | 不同端口但走线可能平行 |

**而 PA5/PA6/PA7 在 GPIOA 上，周围是 USART、CAN 等低速外设，干扰小得多。**

**⇒ 这也解释了为什么 42 MHz 反而更好：引脚干净，速度快不会增加误码，反而缩短了命令帧的持续时间，让芯片的命令仲裁器更容易命中。**

## 五、代码改动（关键部分）

### 5.1 `w5500_port.c` — SPI 选择开关

**文件开头新增可切换的配置块：**

```c
/* ==========================================================================
 *  2026-11-22: SPI selection switch.
 *  Set W5500_USE_SPI1 to 1 AFTER rewiring the module to SPI1 pins.
 *
 *  SPI2 (old wiring):
 *      PB13 SCK / PB14 MISO / PB15 MOSI / PB12 CS / PB10 RST
 *      APB1 = 42 MHz, max SCLK = 21 MHz (prescaler /2)
 *      => commands dropped at 0.656 MHz, and TCP echo only 0/3 at 21 MHz
 *  SPI1 (current wiring, WORKING):
 *      PA5  SCK / PA6  MISO / PA7  MOSI / PA4  CS / PB10 RST
 *      APB2 = 84 MHz, max SCLK = 42 MHz (prescaler /2)
 *      => 12/12 TCP echo, 1KB transfer OK
 *
 *  RST stays on PB10 in both configurations, so it needs its own port macro.
 * ========================================================================== */
#define W5500_USE_SPI1      1

#if (W5500_USE_SPI1 == 0)
  #define W5500_SPI           SPI2
  #define W5500_SPI_CLK_EN()  __HAL_RCC_SPI2_CLK_ENABLE()
  #define W5500_PORT          GPIOB
  #define W5500_SCK_PIN       GPIO_PIN_13
  #define W5500_MISO_PIN      GPIO_PIN_14
  #define W5500_MOSI_PIN      GPIO_PIN_15
  #define W5500_CS_PIN        GPIO_PIN_12
  #define W5500_RST_PORT      GPIOB
  #define W5500_RST_PIN       GPIO_PIN_10
  #define W5500_AF            GPIO_AF5_SPI2
  #define W5500_SPI_PRESCALER SPI_BAUDRATEPRESCALER_2
#else
  #define W5500_SPI           SPI1
  #define W5500_SPI_CLK_EN()  __HAL_RCC_SPI1_CLK_ENABLE()
  #define W5500_PORT          GPIOA
  #define W5500_SCK_PIN       GPIO_PIN_5
  #define W5500_MISO_PIN      GPIO_PIN_6
  #define W5500_MOSI_PIN      GPIO_PIN_7
  #define W5500_CS_PIN        GPIO_PIN_4
  #define W5500_RST_PORT      GPIOB
  #define W5500_RST_PIN       GPIO_PIN_10
  #define W5500_AF            GPIO_AF5_SPI1
  #define W5500_SPI_PRESCALER SPI_BAUDRATEPRESCALER_2   /* 84 MHz / 2 = 42 MHz */
#endif

/* Both GPIOB (RST) and the SPI port clock must be on. */
#define W5500_GPIO_CLK_EN() do { \
        __HAL_RCC_GPIOB_CLK_ENABLE(); \
        __HAL_RCC_GPIOA_CLK_ENABLE(); \
    } while (0)
```

### 5.3 `net_tcp.c` — `Net_TcpPoll()` 改成事件驱动

**改动前的问题：全速轮询（约 45k 次 SPI 事务/秒），且 `SOCK_CLOSED` 只要读到一次就重开 socket —— 而 `socket()` 内部会先 `close()`，等于把正在 LISTEN 的 socket 亲手关掉。**

**改动后的关键点：**

```c
void Net_TcpPoll(void)
{
    static uint32_t s_last_poll   = 0u;
    static uint8_t  s_closed_cnt  = 0u;
    static uint32_t s_closed_tick = 0u;
    static uint32_t s_listen_tick = 0u;

    uint8_t  sr;
    uint16_t len;
    int32_t  ret;

    /* Rate limit to 2 ms. At full speed the poll itself became an SPI
     * noise source and spurious SR reads flapped the socket. */
    if ((HAL_GetTick() - s_last_poll) < 2u)
    {
        return;
    }
    s_last_poll = HAL_GetTick();

    sr = Net_ReadSr();

    switch (sr)
    {
    case SOCK_ESTABLISHED:
        /* clear CON interrupt, then echo RX data back */
        ...
        break;

    case SOCK_CLOSE_WAIT:
        disconnect(TCP_SN);
        break;

    case SOCK_CLOSED:
        /* require 5 consecutive CLOSED reads spanning >= 20 ms */
        if (s_closed_cnt == 0u) { s_closed_tick = HAL_GetTick(); }
        s_closed_cnt++;
        if ((s_closed_cnt >= 5u) && ((HAL_GetTick() - s_closed_tick) >= 20u))
        {
            s_closed_cnt = 0u;
            if (socket(TCP_SN, Sn_MR_TCP, NET_TCP_ECHO_PORT, 0u) == (int8_t)TCP_SN)
            {
                (void)listen(TCP_SN);
            }
        }
        break;

    case SOCK_INIT:
        /* retry LISTEN at most every 100 ms */
        if ((HAL_GetTick() - s_listen_tick) >= 100u)
        {
            s_listen_tick = HAL_GetTick();
            (void)listen(TCP_SN);
        }
        break;

    default:
        /* SOCK_LISTEN and transitional states: do nothing at all.
         * Touching the command register here is what broke LISTEN. */
        s_closed_cnt = 0u;
        break;
    }
}
```

### 5.4 `net_tcp.c` — SR 三取二读取

**高 SPI 速率下单次 VDM 读偶尔会返回错误的 `SOCK_CLOSED`，用多数表决过滤：**

```c
static uint8_t Net_ReadSr(void)
{
    uint8_t a = getSn_SR(TCP_SN);
    uint8_t b = getSn_SR(TCP_SN);
    uint8_t c = getSn_SR(TCP_SN);

    if (a == b) { return a; }
    if (a == c) { return a; }
    if (b == c) { return b; }

    /* All three differ (rare): prefer any non-CLOSED value */
    if (a != SOCK_CLOSED) { return a; }
    if (b != SOCK_CLOSED) { return b; }
    return c;
}
```

### 5.5 `socket.c` — 有界重试（v3 加的，保留）

**ioLibrary 的 `socket()` / `close()` / `listen()` 里加了有界重试，用来补偿命令被概率性丢弃。**

## ★ 重要勘误（2026-11-22 21:20 补充）

**本文第三节"三档配置对比"存在一个混淆变量，需要更正。**

### 实际情况

**从 SPI2 换到 SPI1 的那一步，同时改变了三个变量：**

| 变量 | 换之前 | 换之后 |
|---|---|---|
| 引脚 / 外设 | PB13/14/15（SPI2，APB1） | PA5/6/7（SPI1，APB2） |
| SCLK 频率 | 21 MHz | 42 MHz |
| **杜邦线长度** | **30 cm** | **10 cm** |

### 因此

**本文第四节"为什么换引脚比提速度更关键"的结论不成立** —— 因为线长变化这个变量没有被控制。

**可能的主因有三种，目前无法区分：**

1. **30 cm 杜邦线太长** → 信号完整性差 → 换 10 cm 就好了（与引脚/速度无关）
2. **PB13/14/15 受 LCD(PB3/PB5)、编码器(PB6/PB7) 干扰** → 换到 GPIOA 就好了
3. **SPI 速率是主因** → 42 MHz 有足够裕量

### 如果要区分，需要做这两个对照实验

| 实验 | 引脚 | 线长 | 速度 | 判读 |
|---|---|---|---|---|
| **A** | PB13/14/15（SPI2） | **10 cm** | 21 MHz | 能通 → 线长是主因；不通 → 引脚是主因 |
| **B** | PA5/6/7（SPI1） | **30 cm** | 42 MHz | 能通 → 线长不是主因；不通 → 线长是主因 |

**实验 A 最有价值** —— 它决定"以后布线要不要特意避开 PB13~15"。

### 当前决定（用户已确认）

**SPI1 已确认空闲（全工程唯一使用者就是 W5500），因此 SPI1 永久分配给 W5500。**

- **SPI2 及其引脚 PB13/PB14/PB15 已释放**，可供其他外设使用
- 保留 `W5500_USE_SPI1 = 1` 配置块，便于以后需要时切换回去验证

## ★ 对照实验结果（2026-11-22 21:40 补）

### 四组配置的完整对比

| # | 外设/引脚 | 线长 | SCLK | TCP 回显 | 现象 |
|---|---|---|---|---|---|
| 1 | SPI2 / PB13,PB14,PB15 | **30 cm** | 21 MHz | **0 / 3** | socket 打不开或立即关闭 |
| 2 | SPI2 / PB13,PB14,PB15 | **10 cm** | 21 MHz | **2 / 5** | 部分成功，失败时收到**乱码** |
| 3 | SPI1 / PA5,PA6,PA7 | 10 cm | 21 MHz | **4 / 5** | 偶尔超时 |
| 4 | **SPI1 / PA5,PA6,PA7** | **10 cm** | **42 MHz** | **12 / 12** | **全部正确** |

### 结论：三个因素都有贡献，是"信号质量余量"问题

**每一处改善都降低了误码概率：**

```
30cm + SPI2 + 21MHz   →  0/3    完全不通
10cm + SPI2 + 21MHz   →  2/5    线长改善有一半效果
10cm + SPI1 + 21MHz   →  4/5    换引脚再进一步
10cm + SPI1 + 42MHz   →  12/12  全部改善才稳定
```

**实验 2 中失败时收到的是乱码（如 `??C;??`、`?%p?t??`），而不是超时 ——**
**这说明数据在 SPI 传输过程中发生了位错误，属于典型的信号完整性问题。**

### 对布线的实际指导

| 建议 | 理由 |
|---|---|
| **SPI 信号线用 10 cm 以内** | 30 cm→10 cm 把成功率从 0/3 提到 2/5 |
| **W5500 接 SPI1（PA5/6/7）** | 比 SPD2（PB13/14/15）再提升一档，可能因为 GPIOA 周围干扰源少 |
| **SCLK 用 42 MHz** | 反而比 21 MHz 更稳 —— 在引脚干净的前提下，高速缩短了事务时间 |
| **做产品时必须上 PCB** | 杜邦线在 42 MHz 下的裕量仍然不大 |

### 最终固化配置

**实验 1~4 做完后，用户决定采用组合 4（SPI1 + 10cm + 42MHz）作为最终配置。**

```
W5500_USE_SPI1      = 1
W5500_SPI_PRESCALER = SPI_BAUDRATEPRESCALER_2   /* APB2 84MHz / 2 = 42MHz */
SCK=PA5  MISO=PA6  MOSI=PA7  CS=PA4  RST=PB10
```
