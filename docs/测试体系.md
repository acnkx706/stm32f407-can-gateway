## 2. 七条方法，每条都有出处

### ① 分层验证：一次只验一层

ISO-TP 验完才写 UDS。ISO-TP 不碰 Flash、不碰 UDS，
所以它挂了就一定是分帧问题，不用往下猜。

反例：如果一开始就写"完整刷写流程"，出错时有五种可能（CAN 驱动 / 分帧 /
服务分派 / 擦除 / 搬运），定位成本是分层做法的十倍。

### ② 独立参照：不自己跟自己比

256 字节的判据是"PC 用 Python 算的 CRC16"和"F103 用 C 算的 CRC16"相等。
两套代码、两个平台、同一算法 —— 相等才说明字节一个没丢、一个没翻。

如果只在设备自己内部做一致性检查（写进去再读出来比），
**传输过程本身的错误永远发现不了**。

### ③ 判据是数字，不是感觉

| 用例 | 判据 |
|---|---|
| ISO-TP | `crc=0201` 两边相等 |
| 传输可靠性 | F407 的 `drop=0`、`bad=0` |
| 总线关闭 | F407 的 `rf` 2 秒内增长 **0** |
| 总线恢复 | `rf` 2 秒内增长 **20** |
| 硬件连接 | `ack` 计数不再增长 |

一条都不是"看起来对了"。

### ④ 负向用例和正向一样多

| 类别 | 负向用例 |
|---|---|
| ISO-TP | 漏发第 5 帧（跳号）→ 整包作废；300 字节超缓冲 → 回 OVFLW 拒收 |
| UDS 参数 | 长度不足 `7F xx 13`；子功能不存在 `7F xx 12`；参数越界 `7F xx 31` |
| 会话 | 默认会话关总线被拒；默认会话复位被拒；未解锁复位被拒（`33`） |
| 安全访问 | 没求种子就送密钥（`24`）；密钥错（`35`）；连错三次锁定（`36`） |

**现场真正遇到的是后者，不是前者。**

### ⑤ 可重复执行

`0x27` 那个 bug（切会话没清安全状态）**只在第二遍跑时出现**。
单跑一次永远是对的，所以它躲过了第一次验证。

这条是"测试"和"演示"的分界线：演示跑一次就行，测试要跑一百次一样。

### ⑥ 状态可复位

发现上面那个 bug 之后，测试脚本第一步固定发 `10 01` 回默认会话，
把上一轮残留的种子和解锁状态清干净 —— **每个用例都从已知状态出发**。

### ⑦ 测试工具自己也要自检

`isotp_test.py --crc-only` 不连网就能验拆帧对不对；
`sec_test.py` 的密钥算法在 Python 里独立写一遍；
`run_all.py` 第一版自己就有两个 bug（见下文第 4 节）。

**测试代码出错时，它会告诉你"被测代码错了"。**

## 3. 最快的定位手段：加计数器，而不是加打印

第三次线被碰掉时，现象只有一句"`rf=0`"。

- 只有 `rf=0` 的话，只能猜：ISO-TP 把中断搞坏了？CAN 停了？发送方挂了？
- 加了 `Q` 命令读 `g_can_ack_err` 之后，一句话定案：**`ack` 在涨 = 总线上没人应答**

因为 CAN 的 ACK 是**接收侧硬件行为**，和发送方能不能发无关。
`ack` 涨就说明"帧发出去了，但没有任何节点收对" → 线断 / 没电 / 接反。

**计数器 > 打印**，因为计数器可以远程读数、可以二分、可以放在条件断点里看趋势。

## 4. 统一入口第一次跑，就抓到 3 个问题

这就是"为什么要建统一入口"的最好论据 —— 它抓的不是被测代码的 bug，
是**测试编排本身的 bug**，而那类 bug 平时根本发现不了。

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | ISO-TP 4 组里 2 组"设备没打出 [ISOTP]" | 串口在**发送之后**才打开，而且一打开就 `reset_input_buffer()`，把设备刚打的日志丢了 | ISO-TP 这一组改成原生实现：**先开串口再发帧** |
| 2 | `comm` 组退出码 3（"总线没在跑"） | `sec_test` 结尾会复位设备，`comm_test` 立刻测就撞上"设备还在启动" | 每组之前加 `wait_ready()`：轮询 `rf` 直到增长，最多等 25 秒 |
| 3 | `comm_test` 单独跑也一样 | 它假设"总线已经在跑"，没有等待逻辑 | 把它自己的首步改成带重试的等待 |

**第 2、3 条是同一类错误的两个位置**：把"设备还没准备好"误判成"功能坏了"。
这类假失败在回归里最浪费时间，因为它不是代码坏了，但看报告的人不知道。

## 6. 如果拿它投测试岗，怎么讲

**不要说**"我写了一些测试脚本"。
**要说**"我为一套 CAN-OTA 协议实现建立了回归测试体系：31 个用例、一条命令、
38 秒出结论，覆盖传输层 / 会话 / 安全访问 / 通信控制四层"。

三个可以展开的点：

1. **反向用例占比一半**：31 个里有 15 个是验证"出错时的行为"（拒收、作废、拒绝、锁定）。
   正向只能证明"能用"，负向才能证明"不会坏"。
2. **判据怎么来的**：不是"点一下看看"，是"找一个客观数字"。总线有没有在跑看 `rf`，
   硬件通不通看 `ack`，数据对不对看两套实现的 CRC。
3. **测试编排本身的两个假失败**（第 4 节的 1、2 条）：说明我知道
   "测试不绿"不等于"代码坏了"，得先判断是环境、时序还是代码。

## 7. 遗留：还没做的两组

`0x31`（擦除/校验）已完成并进了套件（第 5 组，8 个用例）。
剩下 `0x34/36/37`（请求下载 / 传数据 / 退出）会真正**写** W25Q64 暂存区。

**为什么放在最后做**：它写坏了要擦整片才能恢复，而前四组已经把
"传输层可靠 + 服务分派正确 + 会话与权限正确" 全部证明了。
先建安全网，再动危险代码。

这一组要用到的新判据：

| 判据 | 怎么看 |
|---|---|
| 擦除期间不超时 | `31 01 FF00` 先回 `7F 31 78`，再回 `71 01 FF00` |
| 块长协商 | `34` 回 `74 20 01 02`（258 = 2 + 256） |
| 块序号校验 | 故意跳一个 blockSeq，回 `7F 36 73` |
| 暂存区写对 | `37` 之后 F103 报 CRC-A 与 PC 一致 |
| 掉电安全 | 擦除中 / 传一半 / 搬运中，各随机断电 5 次 |
